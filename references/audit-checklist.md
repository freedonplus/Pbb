# 生产级审核清单（Audit Checklist）

> 用途：对**已有项目**做生产级审核，或对**本技能产出的项目**做交付前复核。  
> **编号稳定**：每条有唯一 ID（A-01 风格），跨报告、跨版本引用同一缺陷必须用 ID，禁止用序号。  
> **判定四态**：`通过` / `部分通过` / `不通过` / `待验证`；整组不适用时写「不适用 + 一句理由」，逐条不适用并入该组理由。  
> 每条结论必须带**证据**：`文件:行号` / 接口路径 / 配置项名 / SQL / 命令输出。禁止只写「已检查」。  
> 分级：**阻断 P0**（安全、资金与资损、数据丢失、合规违规、无备份单点、不可回滚发布）/ **建议 P1**（影响稳定性与可维护性）/ **记录 P2**（规模化前提）。  
> **去重规则**：同一缺陷命中多条目时，只计入最具体的一条，其余标「见 <ID>」，报告按 ID 计数。  
> **边界声明**：本清单产出的是静态代码审核结果，不是渗透测试，不构成对安全性与可用性的保证。  
> **统计口径（v4）**：核查项 **442 条** + 元规则 4 条（X 组，讲报告怎么写，不计入通过率）= 446 条 / 58 组（Part1 A–AD 30 组 + Part2 攻击面 6 组 + Part3 语言 8 组 + Part4 中间件 6 组 + Part5 治理补缺 8 组）。AI 辅助编码项目必须加载 `security-assurance.md`，AA/AB/AC/AD 不得整组跳过；含 LLM 功能的项目 AL 不得跳过。  
> **每条都带证据等级**（条目前括号内）：`S` 静态可查 / `R` 需运行环境 / `P` 需生产权限。S 类才允许静态下结论；R/P 类无环境时一律「待验证」并写清缺什么。  
> **判定不看「有没有」，看「对不对」**：每条结论必须写全五要素（判定对象 / 合格线 / 证据 / 反例 / 判定），规范见 `verification-standard.md`；具体门槛值见 `acceptance-thresholds.md`。命中反例库 20 种模式之一的，按「部分通过或不通过」处理。

## Part 0 · 结构性扫描手册（大仓库先扫后读）

超过 200 个源文件的仓库，禁止逐文件通读。先用 grep/全局搜索跑下列结构性证据，再对疑点定点读文件：

| 目的 | 模式（按语言调整） | 判读 |
| --- | --- | --- |
| SQL 注入面 | `${` 拼接、`" + ` 出现在 SQL 上下文、`Statement`（非 Prepared） | 命中即人工复核 |
| 定时任务缺失 | `@Scheduled` / `@EnableScheduling` / xxl-job / quartz = 0 处 | 红旗：要么没任务，要么任务在外部系统 |
| 权限覆盖 | Controller 总数 vs `@SaCheckPermission`/`@PreAuthorize`/`[Authorize]` 注解数 | 比值必须 100% |
| 金额精度 | `double` / `float` 出现在 amount/price/balance 字段附近 | 命中即 P0 |
| 明文密钥 | `(?i)(secret\|password\|api[_-]?key\|token)\s*[:=]\s*["'][^"']{6,}` 在 yaml/properties/.env | 命中即 P0 |
| 事务内远程调用 | `@Transactional` 方法体内出现 RestTemplate/Feign/HttpClient/MQ send | 事务边界错误 |
| 先查后改扣减 | `select` 后立即 `update` 同表且无 `where ... >=` 条件 | 超卖/丢更新高危 |
| 异常吞噬 | `catch` 块内只有 log/printStackTrace 无 rethrow/rollback | 事务失效高频原因 |
| 裸线程/默认池 | `new Thread`、`Executors.newFixedThreadPool`、`ForkJoinPool.commonPool` | 无界队列 OOM |
| 日志敏感词 | 日志语句中出现 password/secret/idCard/手机号变量 | 脱敏缺口 |

扫描结果决定「定点深读」的文件清单；结构性扫描本身也作为证据记入报告（如「全仓 grep `@Scheduled` = 0」）。

## Part 1 · 通用生产级审核（A–AD，30 组）

### A. 脱敏与隐私

- [ ] **A-01** （S）是否对脱敏字段处理：手机号、身份证、银行卡、邮箱、详细地址、真实姓名、IP、设备号
- [ ] **A-02** （S）脱敏是否在序列化层统一实现（Jackson Serializer / Pydantic field_serializer / class-transformer），而非各接口手写
- [ ] **A-03** （S）列表页、详情页、导出 Excel/CSV、打印页、开放 API 五处规则是否一致
- [ ] **A-04** （S）日志是否出现完整敏感值（请求体打印、异常堆栈、SQL 参数日志、MQ 消费日志、审计日志）
- [ ] **A-05** （S）加密字段是否密文入库 + 盲索引查询，密钥外置，是否支持密钥版本轮换
- [ ] **A-06** （S）管理端查看完整值是否二次授权 + 审计留痕
- [ ] **A-07** （S）前端是否只渲染后端脱敏结果，而非下发明文后前端遮挡
- [ ] **A-08** （S）第三方回调、对账文件、消息推送、短信模板中是否夹带明文
- [ ] **A-09** （S）导出文件是否加水印/下载者标识，是否限次限量
- [ ] **A-10** （R）测试环境与日志平台的数据是否同样脱敏（生产数据回灌开发是常见违规点）

### B. 认证与授权

- [ ] **B-01** （S）每个接口是否显式声明权限点，有无「登录即可访问」的管理接口
- [ ] **B-02** （S）是否实现数据权限（仅能访问自己的资源），是否有水平越权用例并通过
- [ ] **B-03** （S）垂直越权：普通用户直接调管理端接口是否被拦
- [ ] **B-04** （R）Token 签发、过期、续期、主动失效（踢下线）是否落地
- [ ] **B-05** （S）密码存储是否 BCrypt(cost≥10)/Argon2，是否残留 MD5/SHA1/明文/可逆加密
- [ ] **B-06** （R/P）登录失败锁定、验证码、短信发送频率是否限流
- [ ] **B-07** （S）会话固定、Cookie 属性（HttpOnly/Secure/SameSite）是否设置
- [ ] **B-08** （S）多端登录策略、并发会话上限是否明确
- [ ] **B-09** （S）默认超管账号是否改密或首次登录强制改密；是否存在演示账号残留
- [ ] **B-10** （S）第三方登录（OAuth/微信）回调是否校验 state 与来源

### C. 配置与密钥

- [ ] **C-01** （S）配置是否全部外置（环境变量/配置中心），仓库与镜像中是否残留真实密钥
- [ ] **C-02** （S）敏感项是否无默认值，缺失即启动失败（而非静默使用空串）
- [ ] **C-03** （S）证书、私钥、.env 是否在 .gitignore，历史提交是否清理（git log -S 检索）
- [ ] **C-04** （S）密钥是否有轮换与吊销方案（AES/HMAC/JWT secret/数据库口令）
- [ ] **C-05** （S）生产是否关闭 Swagger/Actuator/pprof/debug 端点或加鉴权
- [ ] **C-06** （S）中间件端口是否只绑内网/本机，是否有 0.0.0.0 暴露风险
- [ ] **C-07** （S）配置项是否有校验（启动时 fail-fast），是否有人改错无人知
- [ ] **C-08** （S）配置变更是否需要重启，是否需要审批与留痕

### D. 数据与事务

- [ ] **D-01** （S）事务是否只在 Service 层，事务内是否有远程调用或 MQ 发送
- [ ] **D-02** （S）事务失效写法：自调用、非 public、异常被吞、非运行时异常未 rollback、多数据源未指定事务管理器
- [ ] **D-03** （R）事务隔离级别是否明确，是否出现长事务（>1s）与锁等待
- [ ] **D-04** （R）是否发生死锁，是否有重试与监控
- [ ] **D-05** （S）唯一索引是否覆盖业务唯一键（订单号、支付流水、幂等键、关系表）
- [ ] **D-06** （S）金额字段是否 DECIMAL/BigDecimal，是否存在 double/float 参与金额运算
- [ ] **D-07** （S）逻辑删除是否与唯一索引冲突，是否用组合索引或归档表规避
- [ ] **D-08** （S）迁移脚本是否版本化（Flyway/Liquibase/Alembic/Prisma）、可回滚、可重放
- [ ] **D-09** （S）大表变更是否用在线 DDL 工具（gh-ost/pt-osc），是否评估锁表时间
- [ ] **D-10** （R/P）备份策略（全量+增量）是否落地，是否做过真实恢复演练并记录 RTO

### E. 索引与 SQL 性能

- [ ] **E-01** （R）核心查询是否走索引，是否被 `explain` 验证（type 不是 ALL）
- [ ] **E-02** （R）是否存在隐式类型转换（字符串列传数字、字符集不一致导致索引失效）
- [ ] **E-03** （R）是否在索引列上使用函数或前导模糊（`like '%x'`）
- [ ] **E-04** （R）联合索引是否符合最左前缀，是否利用覆盖索引避免回表
- [ ] **E-05** （S）是否出现 N+1 查询，是否用批量查询/预加载解决
- [ ] **E-06** （R）深分页（`limit 100000,20`）是否改为游标/延迟关联
- [ ] **E-07** （R）是否有全表 count、无索引 order by、无索引 group by
- [ ] **E-08** （R）慢查询日志是否开启（阈值 1s），慢 SQL 是否有治理闭环
- [ ] **E-09** （S）批量写是否分批提交（每批 500–1000），是否有单事务写十万行的写法
- [ ] **E-10** （S）是否使用 `select *`、返回大字段（TEXT/BLOB）到列表页

### F. 幂等与并发

- [ ] **F-01** （S）下单、支付回调、退款、领券、MQ 消费是否全部幂等，幂等键是否唯一索引兜底
- [ ] **F-02** （R）幂等是否覆盖「请求超时后重试」「用户双击」「网关重放」三种场景
- [ ] **F-03** （S）分布式锁是否在事务外层、粒度是否业务主键、是否设置超时与续期
- [ ] **F-04** （S）锁失效后是否有兜底（唯一索引/状态机 CAS），是否存在「锁一失效就超卖」
- [ ] **F-05** （S）库存/名额扣减是否条件更新（`where stock >= n`）或乐观锁，而非先查后改
- [ ] **F-06** （S）状态机流转是否有前置状态校验（防重复退款、重复发货）
- [ ] **F-07** （S）并发写同一行是否评估热点（计数器、库存）并做分段/队列化
- [ ] **F-08** （R）是否有并发压测或并发用例证明，而非口头保证
- [ ] **F-09** （S）乐观锁版本号是否随每次更新递增，是否存在丢更新
- [ ] **F-10** （S）分布式场景是否存在「先删缓存再写库」等错序操作

### G. 缓存

- [ ] **G-01** （S）穿透：空值缓存/布隆过滤器；击穿：互斥重建/逻辑过期；雪崩：TTL 抖动——三者是否分别有对策
- [ ] **G-02** （S）缓存一致性策略是否明确（Cache Aside / 延迟双删 / binlog 订阅）
- [ ] **G-03** （R）是否有大 key（>10KB 或成员数万）、热 key（单 key QPS 过高）
- [ ] **G-04** （S）key 命名规范是否统一（业务:实体:id:版本），是否设置过期时间
- [ ] **G-05** （R）内存淘汰策略（maxmemory-policy）是否与业务匹配
- [ ] **G-06** （S）缓存击穿时的降级返回是否合理（不返回脏数据）
- [ ] **G-07** （S）缓存与 DB 双写失败是否有补偿
- [ ] **G-08** （S）预热方案是否存在（大促/发版后冷启动）
- [ ] **G-09** （S）本地缓存（Caffeine）与分布式缓存的一致性是否说明

### H. 稳定性与容错

- [ ] **H-01** （S）所有 HTTP/DB/Redis/MQ 客户端是否显式设置连接、读、写超时
- [ ] **H-02** （S）第三方调用是否有限重试（含退避与抖动）、熔断、降级
- [ ] **H-03** （S）重试是否会在故障时放大流量（是否与限流、熔断配合）
- [ ] **H-04** （S）登录、短信、导出、支付接口是否按 IP/用户/全局三档限流
- [ ] **H-05** （S）线程池是否按依赖隔离、队列有界、拒绝策略明确
- [ ] **H-06** （S）是否存在共用默认线程池（ForkJoinPool.commonPool / 全局 executor）
- [ ] **H-07** （S）liveness/readiness 是否分离，readiness 是否检查 DB/Redis 依赖
- [ ] **H-08** （R/P）是否优雅停机（先摘流量 → 等在途请求 → 关闭资源）
- [ ] **H-09** （S）定时任务是否防多实例重复执行（分布式调度或锁）
- [ ] **H-10** （S）启动是否幂等（重复启动不重复初始化数据），是否有启动依赖顺序问题

### I. 消息队列

- [ ] **I-01** （S）生产者是否开启 confirm/ack，是否处理发送失败与本地消息表补偿
- [ ] **I-02** （S）消费是否幂等（业务唯一键 + 去重表/状态机）
- [ ] **I-03** （S）消息是否会丢：持久化、手动 ack、消费异常重试策略是否明确
- [ ] **I-04** （S）重试次数与间隔、死信队列、人工补偿入口是否存在
- [ ] **I-05** （S）顺序消息是否按业务键分区，是否真的需要顺序
- [ ] **I-06** （R/P）积压监控与扩容方案是否存在（消费速率 > 生产速率）
- [ ] **I-07** （S）消息体是否过大（>1MB），是否传 ID 而非全量对象
- [ ] **I-08** （S）延迟消息/定时消息的实现方式是否可靠
- [ ] **I-09** （S）事务消息或最终一致方案是否写清（订单+库存+积分）

### J. 定时任务与调度

- [ ] **J-01** （S）任务是否幂等可重跑，失败是否可续跑
- [ ] **J-02** （S）多实例是否只执行一次（分布式锁/调度中心）
- [ ] **J-03** （R）执行时长是否超预期，是否有超时中断与告警
- [ ] **J-04** （S）任务失败是否有告警与重试，是否有任务执行记录表
- [ ] **J-05** （S）大批量任务是否分片/分批，是否影响在线流量（错峰）
- [ ] **J-06** （S）是否能检测「漏跑」与「重复跑」：调度中心有执行记录，缺失能补偿触发，重复能识别并拦截
- [ ] **J-07** （R）长任务锁是否续期（看门狗），锁过期后第二个实例是否会重复执行同一个任务
- [ ] **J-08** （S）任务依赖是否显式（A 成功后跑 B），上游失败时下游是阻断而非空跑；补数是否会打乱依赖顺序

### K. 支付与资金

- [ ] **K-01** （S）支付回调是否验签、验金额、验商户号，是否拒绝重复与伪造
- [ ] **K-02** （S）回调是否幂等，是否以「渠道流水号」为唯一键
- [ ] **K-03** （S）回调与主动查单是否双保险（回调丢失可补偿）
- [ ] **K-04** （S）金额计算是否全链路整数分或 BigDecimal，是否有精度丢失
- [ ] **K-05** （R/P）是否有时对账（渠道账单 vs 本地流水），差异处理流程是否明确
- [ ] **K-06** （S）退款是否校验可退金额、是否防重复退款、是否原路退回
- [ ] **K-07** （S）资金流水是否只增不改，是否有账务平衡校验
- [ ] **K-08** （S）优惠券/积分核销是否原子（防超发、防重复核销）
- [ ] **K-09** （S）支付渠道密钥是否分环境隔离，是否支持多商户
- [ ] **K-10** （R/P）是否有资损监控与熔断（异常订单量、异常退款量告警）

### L. 文件与对象存储

- [ ] **L-01** （S）上传是否白名单校验类型（MIME + 魔数），是否限制大小
- [ ] **L-02** （S）是否重命名落盘、禁止按原文件名与用户路径拼接
- [ ] **L-03** （S）私有桶 + 预签名访问，链接有效期是否合理，是否可被枚举
- [ ] **L-04** （S）是否存在路径穿越（`../`）、双扩展名、SVG/HTML 内嵌脚本 XSS
- [ ] **L-05** （S）图片是否做压缩/尺寸限制，是否剥离 EXIF
- [ ] **L-06** （S）大文件是否分片上传、断点续传、秒传（hash 去重）
- [ ] **L-07** （R）是否做病毒扫描或至少隔离区，是否禁止上传目录可执行
- [ ] **L-08** （S）删除是否软删 + 延迟清理，是否有孤儿文件清理任务

### M. 可观测性

- [ ] **M-01** （S）日志是否结构化，traceId 是否贯穿入口→DB→下游
- [ ] **M-02** （S）是否存在 printStackTrace、无上下文日志、循环内海量日志
- [ ] **M-03** （S）日志级别是否合理（生产 INFO 起步，无 DEBUG 泛滥）
- [ ] **M-04** （R）指标是否采集：QPS、P99、错误率、连接池、队列积压、JVM/运行时、GC
- [ ] **M-05** （S）告警是否有负责人、阈值依据、处置手册，是否避免告警风暴
- [ ] **M-06** （S）是否有链路追踪（跨服务），是否采样率合理
- [ ] **M-07** （S）关键业务埋点是否可回答「今天下了多少单、失败在哪一步」
- [ ] **M-08** （S）日志轮转与磁盘水位是否受控（避免磁盘打满导致宕机）
- [ ] **M-09** （R/P）是否可在 5 分钟内定位一次线上故障（有无排障入口与手册）

### N. 审计与合规

- [ ] **N-01** （S）审计日志是否覆盖：登录、权限变更、资金操作、数据导出、敏感数据查看
- [ ] **N-02** （S）审计日志是否独立存储、只追加、不可篡改、可检索
- [ ] **N-03** （S）日志保留期是否满足（≥30 天；等保场景 ≥6 个月）

## Part 2 · 攻击面专项（逐项打勾，按 OWASP + 实战高频）

### 注入类
- [ ] **INJ-01** （S）SQL 注入：是否全部参数化/ORM 绑定，是否残留字符串拼接（含 `order by`、`like`、`in`）

- [ ] **INJ-03** （S）命令注入：是否用 `Runtime.exec` 拼接、`child_process.exec` 拼接用户输入
- [ ] **INJ-04** （S）模板注入（SSTI）：用户输入是否进入模板编译（Thymeleaf/Freemarker/Jinja2）
- [ ] **INJ-05** （S）表达式注入：SpEL/OGNL/Aviator 是否解析外部输入
- [ ] **INJ-06** （S）LDAP/XPath 注入（如涉及）
- [ ] **INJ-07** （S）反序列化：是否反序列化不可信数据（Java 原生序列化、Fastjson autoType、Pickle、YAML unsafe_load）
- [ ] **INJ-08** （S）XXE：XML 解析是否禁用外部实体与 DTD
- [ ] **INJ-09** （S）日志注入：用户输入含换行/控制字符是否直接落日志（可伪造日志）

### 文件与路径
- [ ] **FILE-01** （S）路径穿越：文件下载/读取是否校验规范化路径（`../`、绝对路径、软链）
- [ ] **FILE-02** （S）任意文件读取/删除接口是否鉴权

## Part 5 · 治理补缺专项（AE–AL，8 组）

> 补 v2 的三处硬缺口：**服务治理、可观测性治理（SLO）、容量与压测**，另补分布式事务、灰度期兼容、第三方连续性与 LLM 功能输出侧安全。
> 与 Part 1 的分工：M 组管「有没有采集指标」，AG 组管「有没有目标、预算和结论」；U 组管「算没算容量」，AH 组管「压没压过、隔离没隔离、扩不扩得动」；I-09 管「方案写没写」，AI 组管「补偿、对账、演练到位没到位」。
> **必查判定**：微服务 / 多服务协作 / 对外服务项目，AE、AF、AG、AH、AI、AJ、AK 为必查组；单体内部管理系统可整组标不适用，但必须写理由。带 LLM 功能的项目，AL 为必查组。
> 与 Part 1 重复命中时，报告里标「见 <ID>」并在该组记一次，不重复计数。

### AE. 服务间调用与内部接口鉴权

- [ ] **AE-01** （S）内部接口是否逐个鉴权：调用方身份（mTLS / 服务级 JWT / 签名）+ 权限点；内部端点鉴权覆盖率 = 100%，免鉴权白名单显式登记并逐条写理由
- [ ] **AE-02** （S）服务凭据是否绑定工作负载、可自动轮换、有效期 ≤ 24h（ServiceAccount / SPIFFE / 短期 token）；长期共享静态密钥数量 = 0
- [ ] **AE-03** （S）内部写接口是否防重放：timestamp 窗口 ≤ 5min + nonce 去重（TTL ≥ 窗口 1.2 倍），超窗请求是否拒绝而非放行
- [ ] **AE-04** （S）内部接口是否独立做参数校验与越权校验（资源归属、租户隔离）；不得以「上游已校验」为由省略，抽查 3 个内部接口验证
- [ ] **AE-05** （S）管理与内部端点是否与业务端口隔离：actuator / metrics / debug / RPC 端口不对公网开放，独立端口 + 网络策略，默认路径是否改过
- [ ] **AE-06** （R）东西向流量是否 default-deny：命名空间 / 安全组 / NetworkPolicy 白名单，非法出站是否被拦截且有日志
- [ ] **AE-07** （R/P）内部调用是否有审计（调用方、被调方、操作、结果、traceId），可追溯到人/任务；越权与跨租户调用是否有告警

### AF. 服务治理：注册中心 / 配置中心 / 网关

- [ ] **AF-01** （S）注册中心健康检查与摘除参数是否写明具体值：心跳间隔、超时、摘除延迟、保护阈值（如 Nacos protectThreshold），不是「默认配置」
- [ ] **AF-02** （S）配置变更是否灰度 + 一键回滚 + 留痕（谁改的、改前改后、生效实例数、生效时间），是否有变更审批
- [ ] **AF-03** （S）配置中心不可用时行为是否明确：本地快照兜底 / fail-fast，二选一并写明；强依赖配置中心且无兜底 → 不通过
- [ ] **AF-04** （S）网关是否统一承担鉴权、限流、路由、访问日志；路由与限流规则变更是否走审批与审计，是否有绕网关直连后端的旁路（有则须说明）
- [ ] **AF-05** （S）网关超时 / 重试与后端预算是否对齐：重试次数 × 单次超时 ≤ 上游总预算，且重试只对幂等方法开启（否则放大故障，反例 #19）
- [ ] **AF-06** （R）服务发现异常时的降级是否验证过：DNS 缓存、长连接复用、静态地址兜底；实例被批量摘除时是否雪崩（需演练证据）
- [ ] **AF-07** （S）是否有配置漂移检测：多环境关键配置 diff 机制；生产是否存在手工改配置的旁路入口，若有是否审计

### AG. 可观测性治理：SLI / SLO / 错误预算

- [ ] **AG-01** （S）每个对外核心接口是否定义 SLI（可用性 / 延迟 / 错误率），并写明分子分母口径（如「5xx + 超时 / 总请求」，是否排除 4xx 客户端错误）
- [ ] **AG-02** （S）是否设定 SLO 目标值与统计窗口（示例：核心下单 99.9% / 30 天滚动，查询类 99.5%），是否与业务方书面确认
- [ ] **AG-03** （S）是否计算错误预算并配置多窗口燃烧率告警（1h 14.4x / 6h 6x / 3d 1x 三档），而不是只看单点阈值
- [ ] **AG-04** （S）发布门禁是否与错误预算挂钩：预算耗尽 → 冻结非必要发布，仅允许修复类变更；规则是否写在发布流程里而非口头约定（反例 #16 SLO 空转）
- [ ] **AG-05** （S）是否有统一看板：RED（Rate/Error/Duration）+ USE（Utilization/Saturation/Errors）+ 业务指标（下单量、支付成功率），不登机器即可看
- [ ] **AG-06** （S）告警是否分级且有响应时限与升级路径（P0 5min、P1 30min、P2 次日），每级有具名负责人而非「团队」或「所有人」
- [ ] **AG-07** （R）告警质量是否被统计与治理：误报率、静默规则、连续 30 天无动作的告警是否清理，是否有告警收敛（避免风暴）
- [ ] **AG-08** （R/P）是否能在 5 分钟内回答三个问题：现在是否可用、影响多少用户、最近一次变更是什么（需现场演示或录像证据）

### AH. 容量、全链路压测与成本

- [ ] **AH-01** （S）容量模型是否写明：峰值 QPS、单实例容量（压测得出而非估算）、所需实例数、扩容步长与耗时，并列出推导假设
- [ ] **AH-02** （S）是否设水位线与扩容阈值（CPU / 内存 / 连接池 / 队列 ≥ 70% 预警、≥ 85% 扩容），扩容上限与拒绝策略是否明确
- [ ] **AH-03** （R/P）是否做过全链路压测（含下游与 DB），有基线报告：目标 QPS 下的 P99、错误率、资源水位、瓶颈点定位
- [ ] **AH-04** （S）压测流量是否隔离：影子库 / 影子表、流量染色、测试账号标记；压测数据不得进入真实对账、报表与用户可见列表（反例 #17）
- [ ] **AH-05** （S）是否识别热点并给出方案：热点 key（本地缓存 / 拆 key）、热点账户（分段 / 排队）、热点商品（预扣 / 限购），不能只写「加缓存」
- [ ] **AH-06** （S）自动扩缩容是否配置且验证过：HPA 指标、最小 / 最大副本、缩容冷却、PDB；缩容不得把容量砍到水位线以下
- [ ] **AH-07** （S）成本是否可归因与受控：按服务 / 环境 / 存储分账，有预算与超支告警；日志、对象存储、快照有生命周期与归档策略
- [ ] **AH-08** （R）是否有容量评审节奏：大促 / 活动 / 上新前评估，压测结论是否作为扩容与限流的依据，有无复盘记录

### AI. 分布式事务与跨服务一致性（ID 为 AI-xx，与 AA 组「AI 生成代码」无关）

- [ ] **AI-01** （S）跨服务写操作是否显式选型并写明：本地消息表 / 事务消息 / Saga / TCC；两个服务各自 `@Transactional` 当分布式事务用 = 不通过
- [ ] **AI-02** （S）每个正向操作是否有对应逆向操作（取消 / 退款 / 释放库存 / 回滚额度），且逆向操作本身幂等
- [ ] **AI-03** （S）补偿是否有限重试 + 死信 + 人工介入入口；补偿执行有记录表可查（次数、最后错误、操作人、处理时间）
- [ ] **AI-04** （S）是否有对账：T+1 或准实时，差异可定位到单笔，可自动修复或走人工，差异率与处理时长有指标
- [ ] **AI-05** （S）长事务是否拆分，中间态超时是否有兜底：空回滚（Cancel 先于 Try 到达）与悬挂（Try 晚于 Cancel 到达）是否都有防护
- [ ] **AI-06** （S）跨服务重试是否只对幂等方法开启；写操作重试是否带幂等键，避免「超时但已成功」被再执行一次
- [ ] **AI-07** （R）是否演练过「下游成功、上游失败 / 超时」的补偿链路，有演练记录、最终一致性达到时间与失败兜底方式

### AJ. 灰度期兼容与数据演进

- [ ] **AJ-01** （S）DDL 与发布是否遵循 expand → migrate → contract：先加列（可空 / 有默认值）→ 双写回填 → 切读 → 再删旧列；任一步不得让旧版本崩溃
- [ ] **AJ-02** （S）新字段是否向后兼容：可空或有默认值，旧代码读到新数据不抛异常（缺字段按默认处理），不依赖「字段一定存在」
- [ ] **AJ-03** （S）消息体演进是否兼容：新增字段可选、消费者忽略未知字段、不使用严格 schema 校验、不用位置参数数组传参
- [ ] **AJ-04** （S/R）是否有版本协商与契约测试：API 版本、消息版本、消费端兼容性用例，跨版本组合是否被 CI 覆盖
- [ ] **AJ-05** （S）灰度期新旧实例并存时共享状态是否语义一致：缓存 key 带版本 / 前缀、分布式锁 key 不变、状态机遇未知枚举值不崩（反例 #18）
- [ ] **AJ-06** （S）回滚是否安全：新版本写入的数据旧版本能处理；不可逆变更（字段语义改变、删除、加密口径变化）是否有双写双读或快照备份
- [ ] **AJ-07** （R）是否在预发做过「新旧版本混跑」验证，而非只验证新版本单跑；混跑期间的错误率与日志异常是否被检查

### AK. 第三方依赖与业务连续性

- [ ] **AK-01** （S）每个外部依赖是否登记：用途、SLA、超时、重试、降级方案、负责人、密钥归属与到期时间
- [ ] **AK-02** （S）关键依赖（支付、短信、实名、地图、对象存储）是否有多供应商或可切换方案，切换开关是否已实现并可操作
- [ ] **AK-03** （S）依赖不可用时的业务降级是否明确：关闭哪些功能、返回什么、用户看到什么（不是 500 或无限转圈）
- [ ] **AK-04** （S）回调 / 通知是否验签 + 幂等 + 乱序处理 + 重放防护；回调地址是否被当成可信入口（不验签即可改单 = 不通过）
- [ ] **AK-05** （S）外部调用是否有限流与配额控制，避免被下游限流后自身线程池 / 连接池被打满（含连接获取超时）
- [ ] **AK-06** （R/P）是否演练过主供应商不可用：切换耗时、切换后失败率、数据是否需要补对账，是否在业务容忍时间内
- [ ] **AK-07** （S）是否有依赖变更监控：对方 API 版本下线、证书到期、配额调整、条款与计费变更，是否有跟进人与到期提醒

### AL. LLM 功能输出侧安全（项目含 LLM 功能时必查；与 AA 组「AI 写代码」不同）

- [ ] **AL-01** （S）模型输出是否当不可信输入处理：不直接执行、不拼 SQL / Shell、不直接作为 HTML / 富文本渲染、不直接当路由或权限判据（反例 #20）
- [ ] **AL-02** （S）输出渲染是否转义并按白名单处理（Markdown、链接、图片域名），防 XSS、防链接劫持、防外链自动加载
- [ ] **AL-03** （S）是否有输入与输出双向内容安全过滤，命中后的处置流程与留痕（谁、什么内容、如何处理、是否申诉）
- [ ] **AL-04** （S）是否有成本与滥用熔断：单用户 QPS / 日额度、单次上下文上限、日预算上限、超限降级行为（排队 / 降模型 / 拒绝）
- [ ] **AL-05** （S）提示词注入防护：系统提示与用户输入隔离、工具白名单、检索范围按用户权限过滤（模型无权读到无权数据）
- [ ] **AL-06** （S）工具 / 函数调用是否校验参数与权限边界：模型不能凭输出越权调工具，不能传任意 SQL / URL / 命令，写操作是否需二次确认
- [ ] **AL-07** （S）数据与合规：是否声明数据用途与留存期、送第三方前是否脱敏、是否有「不用于训练」约定、跨境传输是否做过评估
- [ ] **AL-08** （S）输出是否可溯源与回放：模型版本、提示词版本、输入哈希、采样参数、token 用量有记录，可复现一次问题回答

## Part 7 · 判定规则

1. **不适用必须写理由**，例如「纯内网工具，无第三方回调 → 支付对账不适用」，一句话即可，不能留空。
2. **无法验证的项标「待验证」**，不臆断为通过；列入报告最后一段，并注明是 R 类还是 P 类、需要什么访问。
3. **阻断项定义**：资金错误与资损、数据丢失、可被未授权访问、密钥泄露、合规违规（明文敏感数据导出等）、无备份单点、不可回滚的发布。
4. **结论门禁**（禁止自由裁量）：
   - 任一 P0 未闭环 → **不可上线**；
   - P0 全部闭环，P1 ≤ 3 条且用户书面接受遗留风险 → **有条件上线**（列出上线后限期补齐项）；
   - 其余 → **可上线**。
   - 待验证项中存在「若为否则属 P0」的，结论最高只能到「有条件上线」，并列出补验证清单。
5. **去重**：同一缺陷按 ID 只计一次；重复命中组标「见 <ID>」。
6. **只建议不代改**：审核模式默认只出报告，不动用户代码与文档；用户明确要求后才进入整改。
7. **偏差登记**：审核中发现实现与文档/方案不一致，记入报告「偏差登记」节，用户确认后再同步文档，并在变更记录留痕。
8. **人工门禁**：AI 辅助开发的 C3/C4 变更缺少独立人工签字、放行单或可执行回滚证据时，按 P0 处理；AI 自审、第二模型复审均不能替代。门禁缺失时结论不得高于「不可上线（流程阻断）」。
9. **复评**：整改完成后走 SKILL.md 阶段 5，出新版报告（v 序号递增），旧版结论与 diff 保留。
10. **运行层不可略过**：有对外服务却无 SLO / 错误预算 / 压测基线的项目，结论最高只能到「有条件上线」，并必须在报告里列出补做计划、责任人与期限；无 SLO 时禁止在报告或方案中出现「生产级」「高可用」等结论性形容词。
11. **治理组不适用要成组说明**：AE–AK 用于多服务协作场景，单体项目可整组不适用，但必须逐组写一句理由（如「单体应用，无内部 RPC 调用 → AE 不适用」），不得整段留空。
