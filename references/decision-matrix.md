# 决策矩阵：答案 → 技术决策

规则格式：`条件 → 决策（理由 / 否决项）`。方案中凡涉及以下主题，结论必须与本文一致；偏离时显式说明。

---

## 1. 架构形态

- 中小型 + 团队 ≤ 5 人 → **多模块单体**。模块划分：启动模块（app）+ common（基础设施）+ 业务模块（按域拆分，各模块只暴露 Service 接口，禁止跨模块直接注入 Mapper）。
  否决微服务：注册中心/配置中心/分布式事务/链路追踪的运维成本远超收益。
- 中大型 + 多业务域 + 团队 ≥ 10 人 → **微服务**。Spring Cloud（Java）/ Go-Zero、Kratos（Go）；按业务域拆分，先拆最独立的域（用户、订单、支付）。
  否决大单体：多团队在同一代码库互相阻塞，发布耦合。
- 不确定 → 默认**多模块单体**，并在方案「架构演进」章节给出「模块 → 微服务」的拆分路径（每个业务模块天然是未来的服务边界，接口先行、实现内聚）。

## 2. 项目结构（多模块单体标准骨架）

以 Java/Maven 为例（其他语言同构）：

```
project/
├── pom.xml                    # 聚合 + dependencyManagement 统一版本
├── project-app/               # 启动模块：Controller 装配、配置文件、启动类
├── project-common/            # common：Result/异常/加解密/Redis/工具类/自动装配
└── project-<domain>/          # 业务模块 × N：按业务域（customer/trade/catalog...）
    ├── controller
    ├── service / service.impl
    ├── mapper / entity / dto / vo
    └── 只依赖 common，不依赖其他业务模块（跨域调用走 Service 接口或 Facade）
```

- 配置文件分层：`application.yaml` 只放 `spring.profiles.active` + 端口；`application-dev.yaml` 全量开发默认；`application-prod.yaml` 全量生产配置，敏感项无默认值、缺失即启动失败。
- 禁止：生产配置继承开发默认值（minio/12345678、localhost CORS、占位密钥）。

## 3. 并发与锁

| 场景 | 决策 |
| --- | --- |
| 库存扣减、抢券、抢票 | **分布式锁（Redisson）+ 乐观锁条件更新双保险**：锁加在事务外层（释放时事务已提交，避免「锁先放、数据后可见」窗口）；SQL 用 `stock - sold >= n` 条件更新兜底 |
| 账户余额、资金变动 | **悲观锁 `SELECT ... FOR UPDATE`** 或余额条件更新 `SET balance = balance - x WHERE balance >= x`；资金不能只依赖 Redis 锁 |
| 状态机推进（订单状态流转） | **乐观锁**：`UPDATE ... SET status=? WHERE id=? AND status=?`，AFFECTED=0 即冲突 |
| 定时任务多实例防重 | Redisson `tryLock` 或 ShedLock；禁止裸跑 `@Scheduled` 多实例 |
| 秒杀级流量（QPS ≥ 1000） | Redis Lua 预扣库存 → MQ 削峰 → 异步落库；DB 只做最终一致写入 |

锁的通用军规：
- 锁必须有超时（Redisson 看门狗优先于固定 expire）；
- 锁 key 必须带业务主键（`lock:departure:{id}`），禁止大粒度全局锁；
- 禁止在锁内调用不可控外部接口（支付、短信），锁持有时间设计目标 < 1s；
- 释放锁用 Lua 保证「判断持有者 + 删除」原子性（Redisson 已内置）。

## 4. 缓存三大问题（有 Redis 必写）

| 问题 | 定义 | 治理方案 |
| --- | --- | --- |
| 穿透 | 查询一定不存在的数据，每次都打到 DB | ① 空值缓存（短 TTL 30–60s）② 布隆过滤器拦截非法 key ③ 参数校验前置 |
| 击穿 | 热点 key 过期瞬间大量请求回源 | ① Redisson 互斥锁重建（同一 key 只放一个线程回源）② 热点数据逻辑过期（不物理过期，后台异步刷新） |
| 雪崩 | 大量 key 同时过期 | TTL 加 ±10% 随机抖动；热点数据不过期 + 主动失效；多级缓存（Caffeine 本地 + Redis）兜底 |

缓存一致性（按业务选）：
- 读多写少、允许秒级不一致 → **Cache Aside + 写后删缓存**（先更新 DB，再删缓存；删失败用 MQ/重试兜底）。
- 对一致性敏感（库存、价格） → **延迟双删**：更新 DB → 删缓存 → 延迟 300–500ms 再删一次（覆盖并发读导致的脏回填）；或 binlog 订阅（Canal）做最终一致。
- 强一致要求 → 不用缓存，或缓存与 DB 同事务边界（仅单机可行），方案中写明取舍。
- 缓存内容军规：只存库内原始数据/相对路径，易变派生物（签名 URL、聚合统计）在出参时生成，不写入缓存。

## 4A. 该不该用缓存（缓存决策矩阵，方案第六章必写）

生产项目最常见的两类错误：**该缓存的没缓存**（热点详情页每次打库），**不该缓存的乱缓存**（强一致数据、低频数据、大列表）。方案必须逐数据对象过一遍下表并给出「用 / 不用 / 可选 + 理由」。

| 数据特征 | 决策 | 理由与注意 |
| --- | --- | --- |
| 读多写少、允许秒级不一致（详情页、配置、字典） | **用** | Cache Aside + TTL；写路径精确失效 |
| 读多写极少、内容大（富文本、图集） | **用**，只存库内原始数据 | 签名 URL 等派生物出参时现算 |
| 强一致实时数据（库存余量、余额、价格判定源） | **不用**（以 DB 条件更新为准） | 缓存只能做展示加速，不能作为判定依据；判定走 `stock - sold >= n` 条件更新 |
| 写多读少（操作日志、流水、行为埋点） | **不用** | 缓存命中率趋近于零，纯浪费内存 |
| 低频访问（月活几次的冷数据） | **不用** | 缓存成本 > 收益 |
| 大列表 / 分页结果 | **慎用** | 容易成大 key；改缓存「条件哈希 → 空结果」或只缓存第一页 |
| 计算代价高、结果可复用（聚合统计、看板） | **可选** | 优先预聚合落库（stat 表），缓存只是第二层 |
| 跨实例共享状态（会话、权限版本、验证码、限流计数） | **用，但不是「缓存」语义** | 用 Redis 当共享存储，必须设 TTL；这类 key 不参与三大问题治理 |
| 热点 key（单 key QPS 高） | **用 + 特别处理** | 逻辑过期 / 本地 Caffeine 一级缓存 / 拆 key |

决策军规：
- 每个用缓存的对象都要同时写出：key 规范、TTL、更新失效策略、属于三大问题中的哪一类风险及对策。
- 每个不用缓存的对象都要写一句理由（防止日后被「优化建议」加回来）。
- Redis 数据结构选型：单值/计数 → String；对象 → Hash；集合去重/交集 → Set；排行榜/延迟队列 → ZSet；基数统计 → HyperLogLog；签到/日活 → Bitmap；简单队列 → Stream（量小且能容忍极小概率丢失时，否则上真 MQ）。

## 5. 幂等（按操作类型选机制）

| 操作 | 机制 |
| --- | --- |
| 创建类（下单/建单） | 客户端 `Idempotency-Key`（UUID）+ Redis `SETNX` 占位（TTL 24h）；同键重复提交返回首次结果；未传键时按「用户 + 业务对象 + 参数指纹」做 30s 窗口去重；业务异常释放占位，不堵死重试 |
| 支付/退款回调 | 以第三方流水号为幂等键，DB 唯一索引兜底；先判状态机再处理，`已处理` 直接返回成功（回调必须可重入） |
| 状态更新类 | 乐观锁条件更新（`WHERE status = 前置状态`），天然幂等 |
| MQ 消费 | 消费端 `msgId` 去重表或 Redis SETNX；所有消费者按 at-least-once 设计 |
| 防重放（对外 API） | `timestamp + nonce + sign`，nonce 一次性、timestamp 窗口 ±5min |

军规：唯一约束是最后一道防线——再完善的锁和去重都必须在 DB 层有唯一索引兜底（订单号、回调流水号、用户+券 领取关系）。

## 6. MQ 选型

| 需求 | 选型 |
| --- | --- |
| 常规异步（通知、邮件、日志收集），中小流量 | RabbitMQ：运维简单、路由灵活；否决 Kafka（杀鸡用牛刀） |
| 订单链路（超时关单、事务消息、顺序消息） | RocketMQ：事务消息保证「本地事务 + 发消息」一致，延迟消息原生支持 |
| 日志管道、行为埋点、大数据同步，吞吐 > 10 万/s | Kafka |
| 只有「延迟任务」一个诉求 | 先用 Redis ZSET 轮询或 RabbitMQ TTL + 死信，不为单点需求引入 MQ 集群 |

通用军规：消费幂等、死信队列必配、消息体只传 ID 不传大对象、生产者 confirm + 消费者手动 ack。

可靠性细节（方案写 MQ 时逐条对应）：
- **RabbitMQ**：Publisher Confirms 只能确认 Broker 收到，不可路由的消息要配 `mandatory` + Return 回调或备份交换器；队列/消息/交换器三者都要持久化；消费手动 ack，失败 nack + 死信交换器兜底；延迟消息用 TTL+DLX 时注意**队头阻塞**（队首大 TTL 会卡住后面小 TTL），改 rabbitmq-delayed-message-exchange 插件。
- **RocketMQ**：事务消息用「半消息 + 本地事务 + 回查」保证本地事务与发消息一致；延迟消息原生支持；顺序消息按业务键投递同一队列；刷盘/复制策略（同步/异步）按丢失容忍度选。
- **Kafka**：`acks=all` + `min.insync.replicas≥2` 才是「不丢」的最低配置；只保证单分区内有序，业务键选分区键；手动提交 offset，消费成功再提交。
- **消费语义**：只承诺 at-least-once，Exactly Once 靠「消费端幂等」实现，不靠 MQ 宣传语。
- **积压治理**：监控 ready/unacked/堆积量；先判断是生产突增、消费变慢还是下游故障，再决定扩容消费者还是降级。

## 7. 分库分表

- 单表 < 500 万行 → **不分**。先做索引、慢 SQL 治理、读写分离。
- 单表 500 万–2000 万 → **垂直拆分优先**：按业务域分库（订单库/用户库/日志库）；日志、流水类大表按月归档。
- 单表 > 2000 万且持续高速增长 → **水平分片**：Java 用 ShardingSphere-JDBC；分片键选查询命中率最高的维度（如 `user_id`），避免跨片 join，需要多维度查询时建异构索引表或走 ES。
- 顺序原则：**索引优化 → 读写分离 → 垂直分库 → 水平分表**，不要跳级。
- 分片后必带：全局 ID（雪花/号段）、跨片分页方案、分布式事务边界说明。

## 7A. 数据库索引设计军规（方案第五章必写索引设计表）

原理底稿见 `bagu-essentials.md` MySQL 章；此处为落地军规。

- **每张核心表列出：查询场景 → 索引（列序）→ 类型 → 理由**。没有索引设计表的方案直接打回。
- **最左前缀**：联合索引按「等值列在前、范围列在后、区分度高的在前」排；`(a,b,c)` 能服务 `a`、`a,b`、`a,b,c` 三类查询，别再重复建 `(a)`。
- **覆盖索引优先**：高频查询只取少数字段时，把返回列包进索引（或接受回表），`EXPLAIN` 的 `Extra` 要看到 `Using index`。
- **索引下推（ICP）**：联合索引中范围列 + 过滤列组合时，靠 ICP 减少回表；写法上保证过滤条件能下推到引擎层。
- **防失效**：① 索引列不做函数加工/运算（`WHERE DATE(create_time)=` 改范围写法）；② 字符串列传参必须带引号，防隐式类型转换；③ 字符集与排序规则全库统一 utf8mb4，防 JOIN 索引失效；④ `OR` 两侧都要有索引；⑤ `LIKE '%x'` 前导模糊必全扫，改 ES 或反转列。
- **回表成本意识**：命中率超过 20%–30% 的查询，优化器会放弃索引走全扫——这不是 bug，用覆盖索引或接受它。
- **大表 DDL**：百万行以上加索引用 gh-ost/pt-osc 或 MySQL 8 在线 DDL，评估锁表与主从延迟；生产禁止直接 `ALTER`。
- **隐藏索引（MySQL 8）**：下线索引先设 invisible 灰度观察，再真删。
- **慢查询治理闭环**：slow log 阈值 1s 开启，定期 `EXPLAIN` 巡检，慢 SQL 进 backlog 消项。

## 8. 加密、脱敏与密钥

| 数据 | 方案 |
| --- | --- |
| 登录密码 | BCrypt（cost 10–12），永不回显、不可逆 |
| 手机号/邮箱 | **AES-256-GCM 密文存储 + HMAC-SHA256 盲索引列**（支持等值查询），展示脱敏 `138****8000` |
| 身份证/实名 | AES-256-GCM；明文查看需单独权限 + 审计日志 |
| 姓名/地址 | 明文 + 展示脱敏（`张*`）；合规要求高时同手机号方案 |
| 支付信息 | 原则上不落地，用第三方 token（微信/支付宝返回的 payment_id） |
| 配置密钥（DB/Redis 密码） | 环境变量或配置中心注入，禁止入库入仓；可选 Jasypt 加密 |
| 文件 | 私有桶/私有目录 + 预签名 URL 限时访问，禁止公开可枚举路径 |
| 密钥管理 | 统一外置（KMS 或环境变量），AES/HMAC 分离；数据加密密钥带**版本号字段**（`key_version`），新数据用新版本加密，历史密文随访问渐进重加密，禁止原地换钥导致旧数据不可解 |

加密军规：
- 加密字段必须同时建**盲索引**（`HMAC(key, 明文)`）才能做等值查询，否则只能全表解密；
- 模糊查询需求不要靠加密实现，改用「分词辅助列」或 ES；
- 日志脱敏在**序列化层**统一做（Logback converter / 自定义 `@Sensitive` 注解），不靠开发自觉；
- 高危接口（支付、改密、提现、导出）加签或二次校验，接口参数不落明文日志；
- **密钥泄露应急预案**（方案第九章必写）：发现凭据泄露（尤其已进 git 历史）→ ① 立即在第三方后台轮换/吊销 ② 评估盗用窗口与损失 ③ 新凭据走环境变量注入并验证 ④ git 历史用 filter-repo/BFG 清除 ⑤ 复盘登记。代码里的清除只是第五步，不轮换等于没处理。

## 9. API 文档与前后端契约（必答项）

对接前端**必须**有机器可读的 API 契约，这是后端的交付物之一。

| 语言/框架 | 推荐方案 |
| --- | --- |
| Java / Spring Boot | **springdoc-openapi（OpenAPI 3）+ Knife4j UI**（推荐）；生产环境关闭文档端点或加鉴权 |
| Go | swaggo/swag 生成 OpenAPI；或手写 `openapi.yaml` 作为唯一契约 |
| Python / FastAPI | 内置 OpenAPI（`/openapi.json`）+ Swagger UI，直接用 |
| Node / NestJS | `@nestjs/swagger` 装饰器生成 |

契约硬要求（写进方案「接口契约」章节）：
1. **统一响应体**：`{ code, message, data, traceId }`；分页统一 `{ list, total, pageNum, pageSize }`。
2. **统一错误码**：业务错误码分段（如 `10xxx` 通用、`20xxx` 用户域），错误码表随文档维护。
3. **HTTP 状态码语义**：4xx 客户端问题、5xx 服务端问题、业务失败用 200 + code 表达，两者不混用。
4. **字段规范**：时间统一 `yyyy-MM-dd HH:mm:ss` + 时区说明；金额统一「分」为单位的整数（或明确 decimal 字符串）；ID 用字符串返回（防 JS 精度丢失）；枚举给出全部取值。
5. **鉴权约定**：Header 名称、Token 前缀、续期策略、401/403 语义。
6. **分页/排序/筛选参数约定**、幂等键 Header（`Idempotency-Key`）必须写进文档。
7. **版本管理**：URL 前缀 `/api/v1` 或 Header 版本；破坏性变更必须升版本。
8. **可交付形态**：OpenAPI JSON/YAML 导出可直接导入 Apifox / Postman / YApi；方案里给出文档地址、更新机制（CI 生成或启动时导出）、示例请求响应。
9. **文档与代码同源**：注解/装饰器写接口上，禁止手写一份与代码脱节的 Word 文档。

## 10. 前后端边界（硬规则）

- 后端的交付边界：**接口 + 契约文档 + 错误码表 + 示例**。到此为止。
- **禁止**：写前端页面/组件、改前端仓库代码、替前端决定交互与状态管理、把业务逻辑塞进前端（前端只做展示与校验提示，真正的校验与权限在后端）。
- 前端提出的字段/接口诉求，由后端评估后在契约层解决（新增字段、扩展枚举、加接口），不在前端做数据拼装来迁就后端缺陷。
- 跨域与登录态属于**后端配置责任**（CORS 白名单、Cookie/Token 策略），但页面如何存 Token 由前端决定，后端只给约定。
- 方案中若发现需求本质是前端问题（渲染、交互、路由），只记录「前端侧需求」并交回，不展开实现。

## 11. 语言陷阱（必查）

- **Java**：金额/比例/任何小数点计算 → `BigDecimal`（`new BigDecimal("0.1")` 或 `BigDecimal.valueOf`），禁止 `double`/`float`；比较用 `compareTo`；除法必须指定 scale 与 RoundingMode；JSON 序列化 BigDecimal 用字符串避免前端精度丢失。
- **JavaScript/Node**：`Number` 是双精度，超过 `2^53` 的 ID 会失真 → 后端 ID 用字符串返回；金额用整数分或 decimal 字符串。
- **Go**：`float64` 同样有精度问题 → 金额用 `int64`（分）或 `shopspring/decimal`。
- **Python**：`float` 二进制浮点 → 金额用 `Decimal`，`quantize` 指定精度。
- **C#/.NET**：金额用 `decimal`；禁止 `async void` 与同步等待异步；DbContext 不跨并发共享。
- **PHP**：启用严格类型，安全比较用 `===`/`hash_equals`；不可信输入禁止进入 include/eval/unserialize。
- **Rust**：内存安全不等于业务安全；请求路径谨慎 `unwrap`，异步任务处理取消与背压，unsafe 必须人工复核。
- 其他语言的生产陷阱统一查 `bagu-polyglot.md`。
- 时区：统一存 UTC 或统一存东八区，二者择一并在方案中写明；禁止混用。

## 12. 依赖基线（按语言给清单）

见 `references/stacks/` 对应文件；语言八股另见 `bagu-polyglot.md`。原则：
- 只列**必要**依赖，能不加就不加（每个依赖都是未来的漏洞与升级负担）；
- 版本由 `dependencyManagement` / lockfile 统一锁定，禁止各模块自选版本；
- 引入任何依赖前确认：维护活跃度、License、是否有已知 CVE、体积；AI 推荐包必须核实官方来源、包名与构建脚本。

## 13. AI 编码与人工放行（强制门禁）

| 变更 | 决策 |
| --- | --- |
| C1 文档/测试/无行为重构 | CI + 1 名代码负责人审核 |
| C2 一般业务 | CI + 契约/回归 + 1 名独立人工审核 |
| C3 认证权限、支付退款、资金库存、密钥、敏感数据、DB 迁移 | 专项证据 + 业务负责人和安全/技术负责人双人独立审核 |
| C4 CI/CD、CODEOWNERS、生产 IAM/网络、签名制品、不可逆操作 | C3 + 发布负责人 + 预发演练 + 回滚/止损方案 |

通用军规：
- AI 不持主干直推与长期生产权限，不自审、不合并、不发布、不修改门禁放行自己。
- 核心业务不变量必须有代码、DB、反例/并发/重放测试、对账/监控四层保护。
- 第二个 AI 模型不是人工审核；扫描全绿不是安全证明；缺少 C3/C4 放行单按 P0 阻断。
- 完整流程、攻击链、应急响应与放行单模板见 `security-assurance.md`。
