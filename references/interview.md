# 分轮提问脚本

每轮最多 4 个问题，使用 AskUserQuestion 工具。选项中推荐项放第一位并标注「（推荐）」。
**每题选项不得超过 4 个**（工具硬上限）；未列出的选项引导用户用 Other 自由输入。
回答会裁剪后续轮次：标注了「剪枝」的轮次在条件不满足时整轮跳过。

**已有材料优先**：用户提供了 PRD / 需求文档 / 旧方案书 / 原型截图时，先从中抽取各题答案，写成「已识别决策清单」请用户确认，只补问清单中的缺口，不逐题重问。

---

## 第 1 轮 · 规模与架构（必问）

本轮目的：确定项目体量与架构形态，决定后面所有中间件问题的深度。

1. **后端语言与生态**（若已知则跳过）
   - Java / Spring 生态（推荐）
   - Go（Gin / Go-Zero / Kratos）
   - Python（FastAPI / Django）
   - Node.js（NestJS）
   （C#/.NET、PHP/Laravel、Rust 等走 Other 输入；无对应 stacks 基线时按 SKILL.md 降级规则处理）

2. **项目规模**
   - 中小型（推荐）：日活 < 10 万、表单/CRUD 为主、单库可承载、团队 1–5 人
   - 中大型：日活 10–100 万、有明显的流量尖峰（活动/秒杀）、数据量千万级以上
   - 大型：日活 > 100 万、多团队协作、明确的多业务域拆分诉求

3. **架构形态**
   - 多模块单体（推荐中小型）：一个进程、Maven/Gradle 多模块（启动模块 + common + 业务模块），部署简单、无分布式事务
   - 简单单体（单模块）：极小型项目、个人项目、MVP
   - 微服务：团队 ≥ 10 人、多业务域独立演进、能接受注册中心/配置中心/分布式事务成本
   - 不确定：由助手依据规模与团队给出建议并说明理由

4. **业务类型与流量模型**（用于判断高并发面）
   - 常规业务（推荐）：后台管理 + C 端浏览下单，读多写少
   - 有明显的写热点：秒杀、抢购、库存扣减、抢票、抢券
   - 内部系统：运营/管理后台为主，无公网 C 端流量
   - IoT / 数据采集：写多读少、时序数据

## 第 2 轮 · 框架与版本（必问，选项随语言变化）

本轮目的：锁定语言版本、框架版本、是否用快速开发框架、依赖基线。

1. **语言版本**（按第 1 轮语言给出推荐）
   - Java：JDK 21 LTS（推荐，可用虚拟线程）/ JDK 17 LTS（生态最稳）/ JDK 8（遗留兼容）
   - Go：最新稳定版（推荐）
   - Python：3.12+（推荐）/ 3.10+
   - Node：Node 20 LTS（推荐）/ Node 22 LTS

2. **框架版本**（按语言）
   - Java：Spring Boot 3.x（推荐，需 JDK17+）/ Spring Boot 2.7（JDK8 兼容）/ Spring Cloud（微服务时必选）
   - Go：Gin（推荐）/ Go-Zero（微服务）/ Kratos（B 站系微服务）
   - Python：FastAPI（推荐）/ Django + DRF
   - Node：NestJS（推荐）/ Express/Koa（仅小项目）

3. **是否基于快速开发框架**
   - 从零搭建（推荐）：结构可控、无历史包袱，配合本方案的多模块骨架
   - 快速开发框架：RuoYi-Vue / JeecgBoot / Pig（Java）；Go-Zero 自带；自带 RBAC/代码生成但魔改成本高
   - 已有项目改造：在现有代码基础上做生产化补齐

4. **构建与依赖基线**（Java 必问，其他语言跳过）
   - Maven 多模块（推荐）
   - Gradle Kotlin DSL 多模块
   - 不确定：按 Maven 推荐

## 第 3 轮 · 数据层（必问）

本轮目的：数据库选型、ORM、分库分表策略。

1. **主数据库**
   - MySQL 8（推荐）：生态最成熟、团队最熟悉
   - PostgreSQL：复杂查询/GIS/JSONB 需求强时
   - SQL Server / Oracle：企业存量约束
   - SQLite/嵌入式：仅单机小工具

2. **ORM 与数据访问**（按语言）
   - Java：MyBatis-Plus（推荐，CRUD 零 XML）/ MyBatis 原生 / JPA（Hibernate）
   - Go：GORM（推荐）/ sqlx
   - Python：SQLAlchemy（推荐）/ Django ORM
   - Node：Prisma（推荐）/ TypeORM

3. **分库分表策略**（依据第 1 轮规模给推荐）
   - 不分库分表（推荐中小型）：单库 + 读写优化足够，后续再演进
   - 垂直拆分：按业务域分库（订单库/用户库/商品库），中大型起点
   - 水平分片：单表超 2000 万行时用 ShardingSphere-JDBC（Java）/ 或业务侧 hash 分片
   - 读写分离：读流量远大于写时先上从库，不动分片

4. **结构化之外的数据**
   - 仅关系库（推荐）
   - + 对象存储（MinIO/OSS，有文件上传就选）
   - + 搜索引擎（ES/OpenSearch，有全文检索/复杂筛选就选）
   - + 时序/宽表（IoT、日志分析场景）

---

## 第 4 轮 · 中间件与异步（必问）

本轮目的：缓存、消息队列、定时任务。

1. **Redis 缓存**
   - 需要（推荐）：会话/权限缓存、热点数据、分布式锁基础；绝大多数项目都需要
   - 不需要：纯内网小工具，接受直接打库

2. **消息队列**（有异步解耦/削峰/延迟任务才选）
   - 不需要（推荐中小型）：先用本地异步/定时任务，量上来再补
   - RabbitMQ：常规业务异步（通知、邮件），中小规模
   - RocketMQ：需要事务消息、顺序消息、延迟消息（订单超时关闭）
   - Kafka：日志流、大数据管道、超高吞吐

3. **定时/延迟任务**
   - 单机调度（推荐）：Spring @Scheduled / ShedLock 防重复；中小项目够用
   - XXL-Job：多实例、可视化管理、失败重试
   - 延迟队列：订单超时、超时未支付自动关单（MQ 延迟消息或 Redis ZSET）

4. **部署形态**
   - Docker Compose 单机（推荐中小团队）
   - Kubernetes
   - 传统虚拟机 + Nginx

## 第 5 轮 · 业务风险面（必问；内部系统可剪枝跳过 2、3）

本轮目的：识别高并发、支付、幂等等高风险面，决定锁/缓存治理/幂等方案深度。

1. **是否存在高并发写场景**（库存、抢券、秒杀、抢票）
   - 无（推荐）：常规 CRUD，按标准幂等处理即可
   - 有，中等并发（QPS < 1000）：分布式锁 + 乐观锁条件更新
   - 有，高并发（QPS ≥ 1000 或秒杀级）：Redis 预扣 + MQ 削峰 + 异步落库

2. **是否接入支付**
   - 不接入：跳过本支付相关推导
   - 第三方支付（微信/支付宝）：回调验签、支付幂等、对账、退款流程
   - 自收银/预付卡：额外需要账务与流水一致性设计

3. **是否接入第三方平台**
   - 微信生态（公众号/小程序/开放平台）：access_token 管理、消息加解密、网页授权
   - 短信/邮件/对象存储等云服务能力
   - 地图/物流/其他 OpenAPI
   - 都不接

4. **幂等敏感操作有哪些**（多选，Other 补充；MQ 消费按 at-least-once 默认纳入设计，不单列）
   - 下单/创建类（防重复提交）
   - 支付回调（防重复通知）
   - 退款（防重复退款）
   - 领券/库存扣减（防超发超卖）

## 第 6 轮 · 安全与合规（必问）

本轮目的：认证授权体系、敏感数据保护、接口防护。

1. **权限认证方案**（按语言）
   - Java：Sa-Token（推荐中小团队，轻量、Redis 权限缓存）/ Spring Security + JWT（生态标准）/ Shiro（遗留）
   - Go：JWT + Casbin（推荐）
   - Python：FastAPI Security + JWT / Django 自带
   - Node：Passport/NestJS Guard + JWT
   并确认权限模型：RBAC（推荐）/ RBAC + 数据权限 / ABAC

2. **敏感数据范围**（多选）
   - 用户手机号/邮箱：字段级加密 + 盲索引 + 展示脱敏
   - 身份证/实名信息：加密存储 + 明文访问授权审计
   - 银行卡/支付信息：原则上不落地，走第三方 token 化
   - 无敏感数据

3. **接口防护等级**
   - 标准（推荐）：登录/短信/导出限流 + 参数校验 + 防 SQL 注入/XSS/CSRF
   - 强化：高危接口加签/防重放（nonce + timestamp）、接口加密、设备指纹
   - 内网服务：网关层鉴权即可

4. **合规要求**
   - 无特殊要求（推荐）：按通用企业标准
   - 等保二级/三级：操作审计、日志留存 ≥ 6 个月、双因子、漏洞扫描流程
   - 出海（GDPR/数据出境）：数据可删除、可导出、区域化存储

---

## 第 7 轮 · 交付与前端协作（必问）

本轮目的：确定 API 文档方案与前后端边界。后端交付到「接口 + 契约」为止，不介入前端实现。

1. **API 文档方案**（按语言给推荐，必答）
   - 代码注解生成 OpenAPI（推荐）：Java springdoc + Knife4j / FastAPI 内置 / NestJS @nestjs/swagger
   - 契约优先（design-first）：先写 `openapi.yaml`，再生成/校验代码（Go、跨团队协作时推荐）
   - 手工维护文档（Apifox/YApi 手写）：仅在无框架支持时接受，需注明同步机制
   - 已有平台：用户指定 Apifox / YApi / 其他（Other）

2. **前端联调方式**
   - OpenAPI JSON 导入 Apifox/Postman（推荐）：后端导出地址 + 联调环境 baseURL
   - 提供 Mock（基于契约生成）
   - 前端已有自己的接口层，只需契约文件

3. **边界确认**（必答，避免越界）
   - 后端只交付接口 + 文档 + 错误码表（推荐）
   - 需要同时输出接口示例代码（curl / 各语言 SDK 片段）
   - 需要联调支持（排查跨域、Cookie、签名问题）——但**不写前端页面**

## lite 路径（极小型项目，3 轮）

触发条件：第 1 轮「项目规模」选了「简单单体（单模块）/ MVP / 个人项目 / 毕设演示」。
不走完整 7 轮，只保留三轮、每轮精简：

1. **技术栈**（合并第 1、2 轮）：语言 + 框架版本 + 数据库 + 是否 Redis，4 问一轮问完。
2. **业务风险**（合并第 3–5 轮）：是否有写热点 / 是否接支付 / 幂等敏感操作（多选）/ 部署形态。
3. **交付边界**（第 7 轮原样）：API 文档方案 / 联调方式 / 边界确认。

方案书章节允许裁剪：「高并发与一致性设计」合并进「数据设计」，「生产保障」只保留部署 + 上线检查单；其余章节照模板。P0 清单不裁剪——再小的项目，密钥外置、参数校验、幂等键也不能省。
