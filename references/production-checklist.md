# 生产级能力清单（查漏用）

产出方案前逐项核对。标注「涉及」必须写进方案；「不涉及」需一句理由。
P0 = 上线前必须，P1 = 随业务量补齐，P2 = 规模化演进。

---

## A. 安全基线（P0）

| 项 | 要求 |
| --- | --- |
| HTTPS/TLS | 全站 HTTPS，HSTS（仅 HTTPS 响应下发），证书续期方案 |
| 安全响应头 | `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy`、`Permissions-Policy`、接口侧 CSP |
| 密码存储 | BCrypt（cost 10–12）或 Argon2，禁止 MD5/SHA1/明文 |
| 敏感字段 | AES-256-GCM 密文 + 盲索引；展示脱敏；密钥外置 |
| 鉴权与越权 | 认证 + 功能权限（RBAC）+ **数据权限**（只能看自己的数据）；每个接口显式声明权限点 |
| 参数校验 | 服务端强制校验（Bean Validation / Pydantic / class-validator），不信任前端 |
| 注入与 XSS | 全部参数化 SQL/ORM 绑定；富文本入库前过滤；输出转义 |
| CSRF | Cookie 会话模式必须校验 Origin/Referer 或 CSRF Token；纯 Token（Header 传递）可豁免但要说明 |
| 文件上传 | 类型白名单 + 大小限制 + 重命名 + 私有存储 + 预签名访问；禁止按原文件名落盘、禁止上传目录可执行 |
| 配置与密钥 | 全部环境变量/配置中心，禁止入库入仓；`.env` 进 `.gitignore`；上线前替换所有示例密钥 |
| 日志脱敏 | 手机号、证件、卡号、密码、Token 在日志序列化层统一脱敏 |
| 依赖安全 | 定期 `mvn dependency-check` / `npm audit` / `govulncheck`；禁止引入有已知高危 CVE 的版本 |

## B. 数据与事务（P0）

| 项 | 要求 |
| --- | --- |
| 事务边界 | 事务只在 Service 层，禁止 Controller 开事务；事务内禁止远程调用与 MQ 发送（改用事务消息或本地消息表） |
| 事务失效场景 | 自调用、非 public、异常被吞、非运行时异常未 rollback —— 方案或代码规范中必须提示 |
| 唯一约束 | 订单号、支付流水、幂等键、业务唯一关系必须有 DB 唯一索引 |
| 连接池 | HikariCP 参数随并发量给（maximumPoolSize ≈ CPU*2~4 / 单请求耗时占比），不写默认值 |
| 慢 SQL | 开启慢查询日志（阈值 1s），核心 SQL 必须走索引；方案列出关键索引 |
| 备份恢复 | 每日全量 + binlog 增量，**必须做过恢复演练**（未演练的备份等于没有备份） |
| 数据迁移 | 用 Flyway/Liquibase/Alembic 管理版本，禁止手工改生产表结构 |

## C. 高并发与稳定性（P0/P1）

| 项 | 级别 | 要求 |
| --- | --- | --- |
| 幂等 | P0 | 下单、支付回调、退款、领券、MQ 消费全覆盖（机制见 decision-matrix §5） |
| 分布式锁 | P1（有写热点则 P0） | Redisson；锁在事务外层；超时 + 业务主键粒度 |
| 缓存三大问题 | P1 | 穿透（空值/布隆）、击穿（互斥重建/逻辑过期）、雪崩（TTL 抖动） |
| 缓存一致性 | P1 | Cache Aside + 删缓存；敏感场景延迟双删或 binlog 订阅 |
| 限流 | P0 | 登录、短信、导出、支付等接口按 IP/用户/全局三档限流；算法用令牌桶/滑动窗口 |
| 熔断降级 | P1 | 第三方调用（支付、短信、地图）必须设超时 + 重试（有限次）+ 熔断；Sentinel / Resilience4j |
| 线程池隔离 | P1 | 不同外部依赖用独立线程池，禁止共用默认池；队列有界 + 拒绝策略明确 |
| 超时 | P0 | 所有 HTTP 客户端、DB、Redis、MQ 均显式设超时，禁止无限等待 |
| 优雅停机 | P1 | `server.shutdown=graceful` + 足够长的 shutdown phase；容器先摘流量（readiness 失败）再 SIGTERM |
| 健康检查 | P1 | liveness / readiness 分离；readiness 检查 DB/Redis 依赖 |

## D. 可观测性（P1）

| 项 | 要求 |
| --- | --- |
| 日志 | 结构化（JSON 或固定 pattern）+ traceId 贯穿；按天/大小滚动，保留 ≥ 30 天（等保要求 6 个月） |
| 分级 | ERROR 必须可告警；禁止 `e.printStackTrace()` 和无上下文日志 |
| 指标 | JVM/进程、HTTP QPS/延迟/错误率、DB 连接池、Redis、队列积压；Prometheus + Grafana |
| 告警 | 错误率、P99 延迟、磁盘、队列积压、证书到期；告警要有负责人和处置手册 |
| 链路追踪 | 微服务或跨多依赖时上 SkyWalking / OpenTelemetry；单体可先靠 traceId |
| 审计日志 | 登录、权限变更、资金、数据导出、敏感数据查看，独立存储不可篡改 |

## E. 部署与交付（P0/P1）

| 项 | 级别 | 要求 |
| --- | --- | --- |
| 环境隔离 | P0 | dev / test / prod 三套独立数据库与中间件，禁止共用；生产凭据不下发开发 |
| 镜像与编排 | P0 | Docker 多阶段构建、非 root 运行、healthcheck；compose 或 K8s 一键起 |
| 配置外置 | P0 | 全部环境变量驱动；敏感项无默认值，缺失即启动失败 |
| CI/CD | P1 | 构建 → 单测 → 镜像 → 部署；支持回滚（镜像 tag 保留 N 个版本） |
| 发布策略 | P1 | 灰度/滚动；数据库变更与应用发布解耦（先兼容旧版本的 DDL） |
| 端口与网络 | P0 | 中间件端口只绑内网/本机；生产关闭 Swagger 或加鉴权 |
| 时区与字符集 | P0 | 容器 TZ、DB 时区、连接串字符集（utf8mb4）统一，方案写明 |

## F. 接口契约（P0，对接前端强制）

| 项 | 要求 |
| --- | --- |
| OpenAPI 文档 | springdoc/Knife4j、FastAPI 内置、swaggo、@nestjs/swagger；可导出 JSON/YAML |
| 统一响应体 | `{ code, message, data, traceId }`；分页结构统一 |
| 错误码表 | 分段编号 + 含义 + 处理建议，随文档维护 |
| 字段规范 | 时间格式+时区、金额单位、ID 字符串化、枚举取值全列 |
| 鉴权约定 | Header 名、Token 前缀、401/403 语义、续期策略 |
| 幂等约定 | `Idempotency-Key` 等 Header 写进文档 |
| 版本管理 | `/api/v1`；破坏性变更升版本并保留过渡期 |
| 文档可导入 | 能直接导入 Apifox/Postman/YApi；禁止只给 Word |
| 环境地址 | dev/test/prod 三套 baseURL 列清楚 |

## H. 业务域 × 能力矩阵（评估方法，方案中给一张表）

生产级不是「全都做」，而是「每个业务域为哪些能力付出工程成本」。用矩阵法自证取舍：

1. 列业务域（按项目实际，参考：登录认证、用户与权限、商品/线路、库存/班期、订单创建、支付回调、退款、客户数据、优惠券、报表、客服工单、文件上传、定时任务）。
2. 列能力（8 项）：缓存、分布式锁、幂等、字段加密、脱敏、限流、异步/MQ、审计日志。
3. 每格判定三态：**必需**（上线前必须做，P0/P1）、**按需**（视业务量启用）、**不涉及**（不引入并说明理由）。
4. 矩阵结论直接驱动第十一章的 P0/P1/P2 清单：必需 → P0/P1，按需 → P1/P2，不涉及 → 写入「不做的事」。

示例判定（可直接复用）：
- 订单创建：幂等**必需**、分布式锁**必需**（库存）、异步**按需**
- 支付回调：幂等**必需**、验签+审计**必需**、缓存**不涉及**
- 客户数据：字段加密**必需**、脱敏**必需**、审计**必需**、缓存**按需**
- 报表统计：缓存**按需**、异步**按需**（大报表导出）、其余不涉及
- 文件上传：限流**必需**、审计**按需**、加密**不涉及**（靠私有存储+签名）

## 查漏提问清单（方案末尾自检）

写完方案后逐条自问，任一答案为「否」则补章节或写明理由：

1. 每个必备 P0 项是否都有对应章节或明确「不适用 + 原因」？
2. 每个技术选型是否给了「选择 / 理由 / 否决项」？
3. 是否列出了具体的中间件参数与容量估算（连接数、QPS、存储增长）？
4. 是否说明了**上线顺序**（先建库、先配密钥、先验证回调）？
5. 是否点明了「上线后必须做但不能自动化」的人工动作（改超管密码、建员工账号、备份演练）？
6. 是否写清了已知风险与未做的取舍（不要假装全都做了）？
7. API 契约是否可导出、可导入、与代码同源？
8. 是否越界做了前端的事？（应严格不做）
