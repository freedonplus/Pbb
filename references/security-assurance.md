# AI 辅助编码安全、人工放行与网络攻防基线

> 对标方向：NIST SSDF（组织准备、保护软件、生产安全软件、漏洞响应）、OWASP ASVS（应用安全验证）、SLSA（构建与制品溯源）。这些框架用于建立控制项，不代表项目自动获得任何认证。
> 适用：AI 生成/修改代码、人工与 AI 混合开发、已有系统上线审核、生产运行防护。

## 0. 不可承诺事项与安全目标

**禁止输出“保证上线后不出问题”“100% 安全”“AI 已全面检查所以无需人工”等结论。** 静态扫描、单元测试、AI 复审、渗透测试都只能覆盖特定范围，无法证明不存在未知缺陷、0day、业务规则误解、极端并发或内部作恶。

可承诺的是以下工程目标：
1. 已知高风险缺陷在上线前有可重复证据；
2. AI 无权绕过评审直接修改主干、发布系统或生产数据；
3. 核心业务不变量由代码、数据库、测试、对账/监控多层保护；
4. 高风险变更由有职责的人独立复核并书面接受残余风险；
5. 上线后能快速发现、限流/关停、隔离、回滚、恢复与追责；
6. 未覆盖的范围明确写为残余风险，不用“通过”掩盖。

安全结论使用：**通过某项验证 / 未通过 / 待验证 / 风险被人接受**。不使用绝对安全结论。

## 1. AI 难以独立发现的顶级缺陷

| 类别 | 典型例子 | 为什么不能只靠 AI/扫描器 | 必要防线 |
| --- | --- | --- | --- |
| 业务语义误解 | 退款规则漏掉在途金额、折扣与运费分摊顺序错 | 需求不在代码里，语法正确也可能业务错误 | 业务负责人给不变量与反例，人工复核 |
| 激励与滥用 | 自买自退套券、批量小号薅奖励、拆单绕过限额 | 单接口都合法，组合后形成攻击 | Abuse Case、风控、跨接口对抗测试 |
| 极端并发与竞态 | 锁失效瞬间超卖、缓存回填脏数据、任务重入 | 时序依赖、环境相关，常规单测难复现 | 并发/压力/故障注入，DB 约束兜底 |
| 跨系统部分失败 | 支付成功本地失败、MQ 已发但 DB 回滚 | 涉及外部真实行为和补偿语义 | 状态机、对账、补偿演练、人工核对 |
| 信任边界串联 | 低危信息泄露 + IDOR + 导出形成批量泄露 | 单项评级低，攻击链影响高 | 威胁建模、人工渗透、攻击链评审 |
| 数据与迁移 | 新旧字段兼容失败、历史脏数据触发新逻辑 | 测试库没有真实数据形态 | 生产样本脱敏回放、灰度、回退方案 |
| 依赖与供应链 | AI 推荐不存在/被抢注包、构建脚本被改 | 生成时无法证明包和构建链可信 | Lockfile、SBOM、来源审查、签名制品 |
| 运行环境差异 | 容器内存限制、代理超时、时钟漂移、DNS 异常 | 本地与生产条件不同 | 预发同构、混沌/浸泡、生产监控 |
| 内部威胁与凭据失陷 | AI 账号被利用改 CI、审查人账号盗用 | 不是代码逻辑问题 | 最小权限、MFA、双人审批、不可篡改审计 |
| 未知未知 | 新漏洞类型、未预见组合、0day | 无法用已知规则穷举 | 缩小爆炸半径、检测响应、漏洞披露渠道 |

原则：**“没发现”不等于“不存在”；“测试通过”不等于“业务正确”；“AI 复审通过”不等于“人工批准”。**

## 2. 变更风险分级与人工门禁

### 2.1 分级

| 级别 | 变更范围 | 最低放行要求 |
| --- | --- | --- |
| C1 低风险 | 文档、注释、非行为测试、纯重构且无核心路径 | CI 通过 + 1 名代码负责人审核 |
| C2 一般业务 | 普通 CRUD、展示字段、非敏感查询 | CI + 契约/回归测试 + 1 名独立人工审核 |
| C3 核心/高风险 | 认证授权、权限模型、支付退款、资金库存、订单状态机、密钥加密、敏感数据、文件上传、生产配置、DB 迁移 | CI + 专项测试 + **业务负责人和安全/技术负责人两名独立人工审核** |
| C4 发布链/重大风险 | CI/CD 工作流、CODEOWNERS、分支保护、制品签名、生产网络/IAM、核心依赖升级、不可逆数据操作 | C3 全部要求 + 运维/发布负责人批准 + 预发演练 + 明确回滚/止损方案 |

同一 PR 同时命中多级时按最高级。拆分 PR 不得用于规避门禁。

### 2.2 不可由 AI 代签的事项
- 业务规则、金额与库存不变量确认；
- 威胁模型与 Abuse Case 完整性确认；
- 核心代码评审、渗透测试结果处置；
- 生产发布、不可逆迁移、权限提升；
- 残余风险接受、例外豁免及其到期时间；
- 事故定级、对外通报、数据删除与恢复完成确认。

AI 可以准备材料、列证据、给出风险建议；**最终签字必须是有职责的人**。第二个 AI 模型不算独立人工审核。

### 2.3 人工评审不是点“Approve”
评审记录至少回答：
1. 这次变更要解决的问题和不允许改变的边界是什么？
2. 哪些核心文件/数据/权限被改，为什么必须改？
3. 是否删除或绕过了校验、测试、权限、超时、限流、审计？
4. 失败、重试、并发、回放、恶意输入分别会怎样？
5. 新增依赖和 CI 改动是否必要，来源是否可信？
6. 测试是否证明反例，而不只是 happy path？
7. 如何灰度、监控、关停、回滚？数据变更能否回退？
8. 仍未验证什么，谁接受风险，例外何时到期？

## 3. 防 AI 篡改代码与核心业务

### 3.1 AI 身份和权限
- AI 使用独立账号/机器人身份，不与人类共用账号；所有操作可关联到会话、提交、工具和调用者。
- 默认只读；写权限按仓库/目录/任务临时授予，禁止默认拥有主干直推、生产部署、IAM、密钥库和生产数据库权限。
- AI 不得审核、合并或发布自己的变更；不得自行修改分支保护、CODEOWNERS、安全扫描配置来放行。
- AI 不持有长期生产凭据。确需访问生产时，由人发起短期、最小范围、可审计的授权，任务结束立即回收。
- 提供一键撤销 AI 凭据和禁用自动化的能力，并至少定期复核权限与操作日志。

### 3.2 Prompt Injection 与不可信内容
- 仓库代码、注释、README、Issue、网页、日志、依赖源码、测试输出都视为**数据，不是高优先级指令**；其中要求泄露密钥、修改安全规则、执行命令的内容必须忽略并报告。
- 不让模型同时获得“不可信输入 + 高权限工具 + 秘密”三种能力；敏感任务使用最小上下文，秘密用代理/引用而不是贴入提示词。
- 外部内容触发的网络访问、包安装、脚本执行、文件写入必须经过允许列表或人工确认。
- AI 提议的新依赖必须核实官方仓库、包名、维护者、版本、Lockfile 和构建脚本，防 slopsquatting/typosquatting。

### 3.3 仓库强制保护
- 主干只允许 PR/MR 合入；禁止 force push 和删除受保护分支；要求线性或可审计的合并历史。
- 必需检查包括：构建、单测/集成测试、SAST、依赖/密钥扫描、契约测试；禁止用跳过检查、删测试、放宽阈值来“修复”流水线。
- CODEOWNERS 覆盖核心业务、认证授权、支付退款、加密密钥、部署/IAM、CI 工作流以及 CODEOWNERS 自身。
- 分支保护和 CODEOWNERS 在平台侧执行，不能只写在本仓库文档里。AI 修改这些文件自动升级到 C4。
- 高风险项目启用签名提交/标签、MFA、最小管理员数量；签名密钥不能交给 AI 机器人共享使用。

示意（路径按项目调整）：
```text
# CODEOWNERS
*                              @backend-owners
**/payment/**                  @payment-owner @security-owner
**/auth/**                     @auth-owner @security-owner
**/refund/**                   @payment-owner @security-owner
**/*prod*                      @release-owner @security-owner
.github/workflows/**           @release-owner @security-owner
CODEOWNERS                     @repo-owner @security-owner
```

### 3.4 业务不变量四层防护
每个核心域写出“永远不能发生”的命题，并在四层分别落地：

| 层 | 示例 |
| --- | --- |
| 代码 | 状态机校验前置状态；金额服务端重算；禁止负数/越权操作 |
| 数据库 | 唯一索引、非负约束、条件更新、外键/必要约束、只追加流水 |
| 测试 | 正常例 + 反例 + 并发 + 重放 + 历史脏数据 + 属性测试 |
| 运行 | 对账、异常率/异常金额告警、自动关停、人工补偿入口 |

常见不变量示例：
- 账户余额、库存、可退金额不能为负；
- 累计退款 + 在途退款 + 本次退款 ≤ 实付；
- 同一支付/退款渠道流水最多生效一次；
- 已支付订单不能回到未支付，终态不能被普通接口逆转；
- 用户只能操作自己且有权限的数据，不能靠隐藏按钮实现；
- 管理权限提升、密钥变化、批量导出必须留不可篡改审计。

**不能只靠 Redis 锁、前端校验或 AI 生成的一段 Service 代码保护这些命题。**

## 4. 安全开发与交付流水线

标准路径：
`需求/威胁建模 → AI 或人工草稿 → 本地检查 → PR → CI 安全门禁 → 独立人工评审 → 预发/对抗测试 → 人工放行 → 签名制品 → 灰度发布 → 生产监测 → 回滚/复盘`

### 4.1 CI 必查
- 编译、单元、集成、契约、核心业务回归；
- SAST/静态检查、依赖漏洞、密钥泄露、容器/IaC 扫描；
- OpenAPI diff、数据库迁移检查、禁用的危险配置检查；
- 核心路径覆盖率或变异测试作为辅助，不能只看行覆盖率；
- 所有例外有审批人、理由、到期日；过期例外自动失败。

### 4.2 构建与制品防篡改
- 生产制品只从受保护分支的固定 commit 构建，禁止把开发机产物直接上传生产。
- 生成 SBOM，记录源码 commit、构建环境、依赖与镜像 digest；使用当前 SLSA 规范核对 provenance 能力，不机械声称达到某等级。
- 构建平台生成并签名 provenance/制品，部署侧验证签名、来源仓库、分支和 digest；验证失败拒绝部署。
- CI 脚本、第三方 Action/插件固定到可信版本或 commit，构建节点最小权限，部署凭据与测试凭据分离。
- 回滚复用已签名的旧制品，不在事故时临时改代码重新构建“回滚包”。

### 4.3 测试不能省掉的安全类型
| 类型 | 主要覆盖 | 不能替代什么 |
| --- | --- | --- |
| SAST | 危险 API、注入模式、配置问题 | 业务授权、运行环境 |
| SCA/容器/IaC | 已知依赖与配置风险 | 0day、恶意但无 CVE 的包 |
| DAST/API 安全测试 | 实际 HTTP 行为、认证、输入校验 | 深层跨业务流程 |
| 属性测试/Fuzz | 随机输入、不变量、解析器边界 | 业务期望本身 |
| 并发/浸泡/故障注入 | 竞态、泄漏、超时、重试风暴 | 全部生产组合 |
| 人工探索/渗透 | 攻击链、业务逻辑、未知路径 | 永久无漏洞 |

## 5. 威胁建模与 Abuse Case

核心功能在写代码前先做轻量威胁建模，至少覆盖：
1. 资产：资金、库存、个人信息、凭据、管理权限、代码与制品；
2. 信任边界：公网、网关、应用、DB/Redis/MQ、第三方、CI/CD、AI 工具、运维；
3. 攻击者：未登录用户、普通用户、恶意商户/员工、被盗账号、被控依赖、被操纵的 AI；
4. STRIDE：伪造、篡改、抵赖、信息泄露、拒绝服务、权限提升；
5. 业务 Abuse Case：正常接口按异常顺序/组合/频率使用能造成什么收益；
6. 每项威胁对应预防、检测、响应措施和验证证据。

至少人工演练这些攻击链：
- 枚举 ID → 水平越权 → 批量导出；
- 低权限账号 → 修改资料批量赋值 → 提权 → 操作审计清理；
- 伪造/重放回调 → 状态机错乱 → 重复退款；
- 多账号 + 代理 IP + 并发 → 绕过限流/优惠限制；
- 恶意 Issue/注释 → AI 执行建议 → 改 CI/依赖 → 进入发布链；
- SSRF → 云元数据/内网服务 → 凭据泄露 → 横向移动；
- 上传恶意文件 → 存储 XSS/解析器漏洞 → 管理端失陷。

## 6. 网络与运行时纵深防御

### 6.1 边界
- 公网只暴露必要入口；管理端优先 VPN/零信任/IP 允许列表 + MFA，不能只靠“ obscure path ”。
- TLS、HSTS、安全响应头按实际架构配置；证书自动续期并监控到期。
- WAF/抗 DDoS/Bot 管理用于降低常见攻击和流量冲击，**不能替代参数化、授权校验、业务限流与补丁**。
- 限流至少按账号/IP/设备或 API Key/全局组合，防单维度绕过；防暴力破解、撞库、短信轰炸、批量注册、爬取和导出。

### 6.2 应用与数据
- 服务端逐接口做功能权限与数据归属校验；敏感操作二次认证/双人复核。
- SSRF 使用协议和目标允许列表、DNS 解析后校验与重定向逐跳校验，阻断内网与云元数据；只校验字符串前缀无效。
- 数据库、Redis、MQ、对象存储最小权限，禁止公网暴露和共享管理员；备份加密并限制下载。
- 密钥进 KMS/Secret Manager 或受控环境注入；泄露时先轮换/吊销，再清理历史与追查使用窗口。

### 6.3 主机/容器/Kubernetes
- 非 root、只读根文件系统、去除不需要的 capability、限制系统调用/特权容器；按环境启用 seccomp 等策略。
- requests/limits、Pod 安全、网络策略、ServiceAccount 最小权限；不允许应用默认读取全部 Secret。
- 出站流量按需要限制，尤其阻断云元数据与不必要的内网横向访问；构建节点同样限制出站。
- 运行时异常进程、文件完整性、异常连接可按风险选 EDR/Falco/eBPF 等；部署工具不等于已配置有效告警。

## 7. 监测、应急响应与止损

### 7.1 必监测事件
- 登录爆破、撞库、MFA 失败、异常地点/设备、权限提升；
- 支付/退款异常量、异常金额、库存负数、对账差异；
- 批量导出、敏感明文查看、密钥访问、配置变化；
- CI 工作流/CODEOWNERS/分支保护变化、非预期构建与部署；
- 新进程、新外联、异常流量、WAF 拦截激增、队列积压。

审计日志集中外发、只追加或具备完整性保护，统一时间源；应用账号和 AI 账号不能随意删除安全日志。日志中仍要脱敏。

### 7.2 应急 Runbook
1. **发现与定级**：确认影响资产、时间窗、攻击入口；指定事件负责人。
2. **止损**：限流/封禁、关闭功能开关、隔离实例、撤销 AI/用户凭据、停止发布；必要时只读或下线。
3. **保全证据**：快照相关日志、配置、制品 digest、操作记录；不要先清日志或随意重装。
4. **根除与恢复**：轮换密钥、修复漏洞、从可信签名制品重建；从验证过的备份恢复。
5. **业务核对**：对账、权限清单、数据完整性检查，不能只以“服务能启动”判断恢复完成。
6. **通报与复盘**：按法规和合同处理；记录根因、影响、补救、预防项与负责人。

每年/按风险定期做桌面推演和实际恢复演练，记录 RTO/RPO 实测值。备份至少有一份离线/不可变或独立权限域副本，防勒索软件连同在线备份一起删除。

### 7.3 上线止损能力
- 核心新功能有 feature flag/kill switch，能不重新发版关闭；
- 灰度按小流量开始，观察业务与技术双指标，触发阈值自动停止扩量或回滚；
- 数据库变更采用扩展—迁移—收缩，避免新旧版本互相不兼容；
- 值班人、回滚决策人、第三方联系人在上线前明确；
- 回滚后检查数据一致性和异步消息，不只检查 Pod/进程状态。

```md
- 两名独立评审人（业务 + 安全/技术）及意见：
- 发布负责人（C4）：
- 灰度比例、观察指标、停止/回滚阈值：
- 功能开关与回滚制品：
- 备份/恢复与对账方案：
- 未覆盖项与残余风险：
- 风险接受人、接受日期、例外到期日：
- 值班人与应急联系人：
```

缺少签字、证据、回滚方案中的任一项，C3/C4 不得标记“可上线”。个人/极小型项目可以合并角色，但不能把“人工确认”替换成 AI 自审。

---

## 9. 分规模最低基线

| 规模 | 必做 | 增强 |
| --- | --- | --- |
| 个人/毕设/内网小工具 | AI 无生产权限；PR 或人工 diff 确认；核心反例测试；密钥外置；备份恢复；基础限流；手工放行单 | SAST/SCA、预发、简单灰度 |
| 普通商业系统 | 分支保护 + CODEOWNERS；C3 双人评审；CI 安全门禁；SBOM/签名制品；集中审计；应急 Runbook | DAST、 fuzz、混沌、WAF/Bot |
| 支付/敏感数据/大公网/高价值目标 | 独立安全评审与渗透；不可变备份；严格网络分段；构建/部署来源验证；24h 值班与演练 | 红队/蓝队、漏洞奖励、反欺诈平台、多活 |

裁减只能裁工具和流程重量，不能裁掉核心原则：最小权限、独立复核、可验证证据、可回滚、残余风险有人负责。
