# 判定式审核规范（可验证性标准）

> 解决的问题：清单条目普遍是「是否……」的问答句，只能查出**缺失**，查不出**错配**。
> 实测（v2 的 384 条口径）：87.5% 是「是否」句式，带具体阈值的仅 9.4%。结果是「有超时」判通过、「超时设成 30 秒」也判通过。
> v4 新增的治理组（AE–AL）已按判定式写法落地，带阈值/参数要求的比例明显提高；但「有阈值」不等于「判定对了」，判定仍按本文五要素执行。
> 本文件定义把条目变成**可判定**的规范。审核报告的一条结论，必须满足本文的五要素，否则视为无效结论。

---

## 1. 条目的五要素

一条可判定的审核结论，必须写全五件事。缺任一要素，该结论不得计入通过率。

| 要素 | 要求 | 反例（无效结论） |
| --- | --- | --- |
| **判定对象** | 明确找的是什么机制、在哪个范围 | 「检查了超时配置」——哪个客户端？哪一层？ |
| **合格线** | 可量化门槛或可枚举判据，见 `acceptance-thresholds.md` | 「已设置超时」——多少算合格？ |
| **证据** | `文件:行号` / 配置项名 / 命令输出 / 日志片段 / 接口响应 | 「看过了，没问题」 |
| **反例** | 什么样的实现看起来有、实际不合格 | 只写正向要求，等于允许糊弄 |
| **判定** | 通过 / 部分通过 / 不通过 / 待验证 | 「基本符合」「应该可以」 |

**写法对照**：

- ❌ `H-01 通过：已设置超时`
- ✅ `H-01 通过：网关 read_timeout=10s（nginx.conf:42）、服务 feign readTimeout=3s（application-prod.yaml:31）、DB socketTimeout=2s（jdbc url 参数）、Redis timeout=200ms（RedisConfig.java:27）；下游逐层小于上游，链路最坏 5.2s < 用户可接受 10s`

第二句才能被别人复核，第一句不能。

## 2. 证据等级（S / R / P）

每条条目必须标注它靠什么方式才能闭环。**S 类才能用静态审核下结论；R/P 类在缺乏环境时一律「待验证」。**

| 等级 | 含义 | 典型证据 | 能否静态闭环 |
| --- | --- | --- | --- |
| **S** | 静态可查 | 代码、配置、文档、SQL、依赖清单、CI 配置 | ✅ 能 |
| **R** | 需运行环境 | 起服务、连库、`EXPLAIN`、压测、日志、抓包、并发用例 | ⚠️ 需测试/预发环境 |
| **P** | 需生产权限 | 生产监控、真实压测、演练、审计日志、云控制台 | ❌ 需授权 |

标注规则：
- 组内条目性质一致时用**组级默认**，个别条目另行标注，标注优先级高于默认。
- 报告中「待验证」项必须写清：缺哪个环境、需要什么权限、由谁提供、预计何时补。
- **禁止**把 R/P 类默认写成「通过」；也**禁止**因为没环境就整组跳过——整组不适用要写一句理由。

## 3. 反例库：20 种「看起来通过、实际不合格」

这是本规范最核心的部分。清单判「有没有」，反例库判「是不是真的有效」。审核时逐条对照，命中即按**部分通过或不通过**处理。

| # | 模式 | 看起来通过 | 实际不合格 | 识破方法 |
| --- | --- | --- | --- | --- |
| 1 | **超时倒挂** | 每层都设了超时 | 网关 30s → 服务 30s → DB 30s，实际链路 60s 才失败，重试再放大 3 倍 | 逐层列出超时值，验证「下游 < 上游」且累加 ≤ 用户可接受等待 |
| 2 | **幂等无兜底** | 有 Redis SETNX 占位 | Redis 抖动或主从切换后占位丢失，DB 出现重复单 | 查幂等键是否有 DB 唯一索引，而不是只有 Redis |
| 3 | **权限注解脱漏** | Controller 上都有权限注解 | 类级注解 + 方法级 `permitAll`，或权限点写成 `*:*` 通配 | 统计「接口数 vs 有效权限点数」，检查通配符与白名单 |
| 4 | **脱敏在前端** | 列表页显示 `138****8000` | 接口响应体里是明文，前端遮挡 | 直接 curl 接口看原始响应，不看页面 |
| 5 | **备份没演练** | 每日备份任务成功 | 从未做过恢复，RTO 未知，备份文件可能早已损坏 | 要**恢复记录**与实测 RTO，不要备份成功日志 |
| 6 | **熔断永不触发** | 配了 Sentinel/Resilience4j | 失败率阈值 99%、统计窗口 1s 样本不足、最小请求数 100 从未达到 | 看规则的实际参数值，不看「有没有引入组件」 |
| 7 | **限流可绕过** | 登录接口有限流 | 只按 IP，换代理即绕过；或按账号，但攻击者枚举账号绕开 | 测多维度组合（IP + 账号 + 设备），测分布式换 IP |
| 8 | **索引存在但失效** | 表上有 `idx_create_time` | 查询写 `WHERE DATE(create_time)=?`、字符串列传数字、字符集不一致 | `EXPLAIN` 看 type 与 key，不看索引是否存在 |
| 9 | **唯一索引与软删冲突** | 订单表有唯一索引 | 逻辑删除后同业务键无法再插入，代码里 catch 吞掉异常继续 | 看唯一索引是否含 `deleted` 或走归档表 |
| 10 | **审计可被删** | 有审计日志表 | 应用账号对该表有 DELETE 权限，或与应用库同实例同账号 | 查账号授权，不只看有没有这张表 |
| 11 | **密钥与密文同库** | 敏感字段已加密 | 加密密钥明文存在同一库的配置表里 | 查密钥存放位置与权限，加密不等于保护 |
| 12 | **CI 有名无实** | 流水线里有 SAST 阶段 | 步骤带 `continue-on-error: true`，或只在非主干分支跑，或从未真正执行 | 看最近 30 天的执行记录与退出码，不看 yml 写了什么 |
| 13 | **灰度无判据** | 声称有灰度发布 | 直接全量，或灰度后不看指标就扩量，无回滚阈值 | 要灰度记录：比例、观察时长、指标值、扩量决策人 |
| 14 | **缓存错序** | 用了 Cache Aside | 写成「先删缓存再写库」，并发下脏数据回填 | 看代码执行顺序，不看有没有用缓存 |
| 15 | **内网裸信** | 服务拆分清楚、边界明确 | 内部接口无鉴权，「内网」被当成安全边界；一旦边界被穿透即可横向移动 | 抽内部 RPC 端点看有没有调用方身份与权限点（AE-01） |
| 16 | **SLO 空转** | 有 Prometheus + Grafana + 告警 | 没有 SLI 口径、没有目标值、没有错误预算，告警阈值是随手填的绝对值，发布照样全量 | 要 SLO 定义、统计窗口、燃烧率规则与「预算耗尽怎么办」（AG-01~04） |
| 17 | **压测污染** | 压测报告很漂亮 | 直接压生产库，压测数据进了报表、对账与用户列表，事后靠删数据补救 | 查影子库/流量染色/测试账号标记，查压测数据的清理记录（AH-04） |
| 18 | **灰度不兼容** | 灰度发布流程完整 | 新版本加字段、改语义，旧实例反序列化失败或状态机遇未知枚举值崩溃 | 查 expand→migrate→contract 顺序、字段可空、未知枚举兜底，查混跑验证（AJ-01~05） |
| 19 | **重试放大** | 网关、RPC、DB 都配了重试 | 3×3×3 = 27 倍流量打向下游，故障时把下游彻底打死，超时预算被重试吃光 | 逐层相乘算最坏放大倍数，验证 ≤ 上游预算，且写操作重试有幂等键（AF-05 / AI-06） |
| 20 | **输出直渲** | LLM 功能能跑通、体验不错 | 模型输出直接 `innerHTML` 或拼进 SQL/Shell，提示词可被用户改写工具调用，成本无上限 | 查渲染路径、工具白名单、上下文与预算上限、输出过滤与留痕（AL-01~06） |

使用方式：报告每条不通过/部分通过的结论，注明命中哪个模式编号（如「命中反例 #1 超时倒挂」），便于跨项目统计高频模式。

## 4. 四态判定与写法

| 判定 | 使用条件 | 必须写 |
| --- | --- | --- |
| **通过** | 证据齐全且达到合格线 | 证据 + 实测值 + 合格线 |
| **部分通过** | 机制存在但未达线，或缺覆盖范围 | 已达什么、缺什么、补齐后的判定条件 |
| **不通过** | 机制缺失或明确违反 | 证据 + 不合格点 + 影响面 + 是否 P0 |
| **待验证** | R/P 类且无环境/权限 | 缺什么环境、需要什么权限、谁提供、何时补 |

**禁用表述**：已检查、基本符合、应该没问题、符合行业惯例、暂未发现问题、未发现明显风险。
这些词在报告里等于没写——复核者无法重新走一遍你的判断。

## 5. 判定一致性校验（防「同一系统两个人判出两种结果」）

条目质量不看写得多漂亮，看两个人判得一样不一样。

1. 审核开始前，随机抽 **30 条**，由两名审核人（或两名不同人分别用 AI 辅助）**独立判定**同一系统。
2. 计算分歧率 = 判定不一致条数 / 30。
3. **分歧率 ≤ 10%（≤3 条）** 视为条目可用；超过则说明条目定义模糊，先修条目再继续审核。
4. 分歧条目必须记录：各自判据、分歧原因、最终以哪个为准、条目是否需要改写。

单人项目降级做法：同一人隔天重判一次，或对判定为「通过」的条目做**反向抽检**——随机抽 20 条已通过的，去验证它是不是命中反例库。反向抽检命中率 > 15%，说明这一轮审核的通过结论不可信。

## 6. 阈值来源与项目化调整

- 具体门槛值见 `acceptance-thresholds.md`；该表给的是**常见行业基线**，不是唯一正确答案。
- 项目可按业务调整，但必须满足三条：
  1. 在报告头部或方案书里**书面声明**调整了哪几项、调到多少、依据是什么（业务 SLA、监管要求、历史事故）；
  2. 调整方向只能更严或等价，**放宽必须由业务负责人签字**并写明风险；
  3. 调整项在下一轮复评时必须重新核对，防止「一次放宽永久默许」。
- 阈值与业务无关时（如「密码必须 BCrypt」）不允许调整。

## 7. 可脚本化的 S 类扫描项

以下 S 类可固化为 grep/脚本，减少人工成本。脚本结果本身即为证据，但**只能证明「有没有」，仍需人工判「对不对」**。

| 目的 | 模式（按语言调整） | 说明 |
| --- | --- | --- |
| 金额精度风险 | `double\|float` 出现在 amount/price/balance/fee 附近 | 命中即人工复核 |
| 明文密钥 | `(?i)(secret\|password\|api[_-]?key\|token)\s*[:=]\s*["'][^"']{6,}` | 在 yaml/properties/.env 中扫 |
| SQL 拼接 | `" + ` 出现在 SQL 上下文、`Statement`（非 Prepared） | 结合上下文判 |
| 事务内远程调用 | `@Transactional` 方法体内出现 RestTemplate/Feign/HttpClient/MQ send | 人工确认边界 |
| 先查后改扣减 | `select` 后立即 `update` 同表且无 `where ... >=` 条件 | 幂等/超卖高危 |
| 异常吞噬 | `catch` 块内只有 log/printStackTrace 无 rethrow/rollback | 事务失效高频原因 |
| 裸线程/默认池 | `new Thread`、`Executors.newFixedThreadPool`、`ForkJoinPool.commonPool` | 无界队列 OOM |
| 权限覆盖 | Controller 方法数 vs 有效权限注解数 | 比值必须为 100% |
| 锁顺序 | 多处 `synchronized`/`lock()` 的加锁顺序是否一致 | 死锁预防 |
| CI 空转 | `continue-on-error`、`if: false`、`|| true` 出现在安全扫描步骤 | 反例 #12 |
| 内部端点裸奔 | RPC/内部 Controller 无 `@PreAuthorize`/鉴权过滤器；`permitAll` 出现在非白名单路径 | 反例 #15，AE-01 |
| 重试放大 | 网关 / Feign / Ribbon / DB 连接层同时出现 `retry`/`maxAttempts`/`RetryTemplate` | 逐层相乘算放大倍数，反例 #19 |
| 破坏性 DDL | `DROP COLUMN`、`RENAME COLUMN`、`MODIFY` 改类型，与代码发布同批 | AJ-01 高危，反例 #18 |
| 未知枚举兜底缺失 | `switch` 无 `default`、`Enum.valueOf` 无 try、反序列化配置 `FAIL_ON_UNKNOWN_PROPERTIES=true` | AJ-03/05，反例 #18 |
| 模型输出直渲 | `innerHTML`、`v-html`、`dangerouslySetInnerHTML` 接收模型返回变量 | 反例 #20，AL-01 |

## 8. 与主流程的衔接

- **方案阶段（阶段 2）**：写「生产保障」「安全体系」章节时，每条 P0 必须给出合格线，写不出合格线的条目不算 P0（沿用原有规则，此处补上「阈值从哪来」）。
- **审核阶段（阶段 4）**：逐条按五要素出结论；报告头部声明「本次判定采用判定式规范 v3，阈值表版本 acceptance-thresholds v3，项目化调整 n 项」。
- **复评阶段（阶段 5）**：只复核未闭环项与新证据，沿用同一阈值，不得中途改判据。
- **报告模板**：阻断/建议项表格增加「合格线」与「实测值」两列，见 `audit-checklist.md` Part 6。
